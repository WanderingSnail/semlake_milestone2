# Author Response to Reviewers and Revision Changelog (Milestone 4)

**Manuscript:** *SemLake: Zero-Copy Branching and Three-Way Semantic Merging for Data Lakehouses*  
**Author:** Xiaofan Cao (Qatar University)  
**Reviewed Draft:** 2 November 2026 (`SemLake-XiaofanCao.pdf`)  
**Revised Manuscript:** `paper/semlake_pvldb.tex` / `paper/semlake_pvldb.pdf` (12 pages of main body + 1 page of references)

We thank both reviewers for their thorough reading of our manuscript and their detailed technical critiques. In working through the reviews, we uncovered and fixed an important benchmark bug in our original shared-file (`W1`) merge driver (which had marked files as touched without generating row-level operations, understating summary and delta-manifest payload sizes), tightened our formal contract (`purge-wins` on delete-vs.-update conflicts, reader-visible semantics and a publish gate for open VSA choice nodes, pre-image pruning with a soundness proof, and removal of the lossy `int64 -> double` promotion), and rebuilt our evaluation around a query-result oracle over 17 full TPC-H queries with joins and subqueries, fair `B1R` and group-commit baselines across all storage and concurrency experiments, a per-object storage ledger, a $10^3$ to $10^6$ row delta-size sweep, P50/P99 latency bands, and 2,400 fault-injected crash-recovery tests.

Below, Section 1 provides the summary revision matrix across Reviewer 1, Reviewer 2, and the Milestone 4 rubric; Section 2 gives our point-by-point response to Reviewer 1 and Reviewer 2; Section 3 documents the claims from the 2 November draft that were corrected or withdrawn after fixing the benchmark bug and running the new controls; Section 4 summarizes the code, test, and artifact additions; and Section 5 lists the one-command verification steps.

## 2. Detailed Point-by-Point Response to Reviewers

### Response to Reviewer 1 (`49216155.pdf`)

> **R1-W1 & R1-S1 (Prototype memory model and dataset scale in merge experiments):**  
> *"First, the prototype relies on in-memory storage for row-level modifications. Some merge experiments were conducted using the 'TPC-H SF 0.01' dataset, a relatively small-scale dataset, which is insufficient for evaluating scalability in large-scale data environments... It is recommended to expand the scope of the empirical evaluation to include larger datasets, particularly in merge tests, to verify scalability in more realistic environments."*

**Response:**  
Thank you for pointing this out. Because SemLake's two-tier conflict check operates exclusively on commit summaries without reading base Parquet data files, merge verification cost depends on the number of changed or deleted rows ($|\Delta_{\text{rows}}|$) and the number of declared predicates ($|\Pi|$) rather than total table size. To test scalability along the dimensions that actually drive merge cost, we added two sets of experiments:
1. **Delta-size and predicate-count sweep up to $10^6$ changed rows (Section 7.3, Figure 5 / `fig_sweep.pdf`):** We sweep branch purges and updates from $10^3$ to $10^6$ rows against a concurrent report branch, and sweep read predicate counts from 1 to 64 at $10^5$ deleted rows. At $10^6$ deleted rows, SemLake completes the three-way merge and two-tier verification in **16.4 s** (P50; P99 **17.1 s**) with a peak resident memory footprint of **4.9 GB** and a **213 MB** commit summary, scaling linearly at **16 $\mu$s** and **4.9 KB of memory per changed row**. We also added a vectorized Arrow/DuckDB evaluation pass (`VECTOR_THRESHOLD = 2000` rows in `semlake/verification.py`) that evaluates clauses in a single table scan over the recorded delta rows rather than a per-row Python loop.
2. **Full 77-pair TPC-H merge benchmark at `SF 0.1` (600,572 rows, Section 7.2) and `SF 1` (6,001,215 rows) scan lifecycle (Section 7.5):** All 77 TPC-H delete and update/insert branch pairs are evaluated at both `SF 0.01` and `SF 0.1`, and we state explicitly in **Section 7.3** and **Section 9** that full-table snapshot overlays in the Python prototype are kept in memory (`RowView`), which bounds full-table branch-pair tests to `SF 0.1` while delta-summary verification scales to $10^6$ changed rows per merge.

---

> **R1-W2, R1-W4 & R1-S2 (Complex SQL queries with joins/subqueries and false-conflict rates outside $\mathcal{F}$):**  
> *"Second, the accuracy of conflict detection depends on logging declared reads operations; however the verification mechanisms does not fully cover complex SQL queries, such as those involving joins or subqueries... Lastly, an aspect that warrants further evaluation is how the Two-Tier Predicate Verification mechanism handles queries that fall outside the Decidable SQL Predicate Fragment, specifically those involving joins or subqueries. Given the use of a conservative verification mechanism, this may lead to the reporting of false conflicts. Therefore, it is suggested to measure the frequency of these conflicts and their impact on merge operations efficiency by using more complex queries."*

**Response:**  
We completely agree. In the reviewed draft, multi-table queries either had their `lineitem` filter extracted manually or were flagged conservatively as un-evaluable. We have extended both the theory and the implementation to handle multi-table joins and subqueries automatically, and we now measure false-block rates directly against a ground-truth query-result oracle:
1. **Per-block single-table projection of joins and subqueries (Definition 3.6 and Lemma 5.1, Sections 3.4 and 5.1):** Given an arbitrary SQL query $Q$ reading the merged table $R$, our SQLGlot extractor (`semlake/sql_predicates.py`) decomposes $Q$ into query blocks. For each block $b$ referencing $R$ through inner joins, it constructs the projected predicate $\pi_R(b)$ from the block's `WHERE` and `ON` clauses by replacing any sub-condition referencing another table, subquery, or correlated outer column with `TRUE` (dropping foreign conjuncts and widening foreign disjunctions to `TRUE`), while blocks using outer, semi, or anti joins on $R$ project to `TRUE`. Lemma 5.1 proves that this monotone relaxation is sound: if no changed row crosses $\pi_R(b)$ or alters the projected columns $C_Q$ inside $\pi_R(b)$, then $Q(R) = Q(R')$.
2. **Evaluation on all 17 full TPC-H queries reading `lineitem` under a query-result oracle (Section 7.2, Table 6 / `tab_fullqueries.tex`):** We run the unmodified SQL of all **17 TPC-H queries that touch `lineitem`** (Q1, Q3–Q10, Q12, Q14, Q15, Q17–Q21), plus `count(*)` and a filtered `SELECT *` (19 read branches total), against 15 refresh branches (7 deletes, 7 updates, 1 insert = **285 branch pairs**, of which 51 actually change the query's final output). Table 6 reports recall, precision, and false-block rates broken down by query class:
   - Across all 285 pairs, SemLake achieves **1.00 recall** (0 missed result changes), **0.41 precision**, and a **31% false-block rate** on safe pairs, compared to a **69% false-block rate** (precision **0.24**) for the Delta-style file-level read check (`B1R`) and **0.00 recall** for row-level merges (`B2`).
   - By query class, SemLake's false-block rate is **0%** on single-table queries (precision **1.00**), **27%** on inner-join queries with a local `lineitem` filter (precision **0.30**), **14%** on queries with subqueries (precision **0.44**), and **62%** on the 6 queries (32% of reads: Q5, Q8, Q9, Q17, Q18, Q21) that filter `lineitem` solely through join partners and therefore project to $\pi_R(b) = \textsc{true}$.
   - Switching off the per-block projection (Table 9, Section 7.6) causes the false-block rate on full TPC-H queries to jump from **31% to 80%**, and using the Tier-1 static solver alone raises it to **48%**.

### Response to Reviewer 2 (`49216156.pdf`)

> **R2-MC3 (Reconciling object-store accounting, the 380-byte merge, lifecycle WAF with compaction, and crossover CI range):**  
> *"Section 7.4 reports the W1 merge as 3 PUT, 3 GET and 1 LIST, 'writing 380 bytes of metadata', although the delta manifest lists the files whose DVs changed, here 10,000... **Response:**  
Your observation about the 380-byte merge uncovered a genuine bug in our original `workload_w1s` benchmark driver (`benchmarks/workloads.py`): the driver had touched file metadata entries without recording row-level `update`/`delete` operations, causing the merge to emit an empty delta manifest (380 bytes) with no deletion vectors!

> **R2-MC4 (Verification complexity bound, delta/predicate scaling sweeps, and explaining Figure 4b file-count growth):**  
> *"Section 4.4 gives the deleted-row check a cost of O(|DX|) per clause pair and Unstable a cost of O(|UX|) per read predicate, while Section 5.2 states O(|ΠA|·|ΠB| + |Δrows|)... Sweep deleted and changed rows into the millions and predicate counts into the tens, reporting merge CPU, memory and summary bytes. State the assumption behind the Section 5.2 bound or give the worst case, and explain the file-count growth in Figure 4b."*

**Response:**  
1. **Corrected worst-case complexity bound (Section 5.2):** We updated Section 5.2 to state the exact worst-case verification time $O(|\Pi^D|\cdot|\Pi^R| + |\Pi^R|\cdot|\Delta_{\text{rows}}|)$, where the first term is Tier-1 static satisfiability and the second term evaluates each read predicate once (caching the result across delete clauses) over the changed/deleted rows of the partner branch, and we explicitly note that our earlier $O(|\Pi_A|\cdot|\Pi_B| + |\Delta_{\text{rows}}|)$ expression assumed a bounded number of read predicates per merge.
2. **Million-row and 64-predicate sweeps (Section 7.3, Figure 5 / `fig_sweep.pdf`):** As detailed in our response to R1-W1, Figure 5 sweeps $|\Delta_{\text{rows}}|$ from $10^3$ to $10^6$ rows and $|\Pi^R|$ from 1 to 64 clauses (at $10^5$ deleted rows, merge time grows linearly from **0.71 s** at 1 read clause to **4.59 s** at 64 read clauses, directly exhibiting the $|\Pi^R|\cdot|\Delta_{\text{rows}}|$ term).
3. **Explanation of Figure 4b (`1K` to `10K` files, Section 7.3):** Profiling the earlier $8\times$ CPU growth from 1K to 10K files revealed that our previous commit path wrote a full $N_{\text{files}}$-entry manifest on every commit, which the merge then parsed in Python. After introducing delta manifests (`semlake/metadata.py`), merge CPU at 1K to 10K files is **0.81 ms to 3.55 ms** (Figure 4b); profiling confirms that the merge itself does $O(|\Delta_{\text{files}}|)$ work and that the remaining $4.4\times$ growth in the in-memory benchmark comes from `MemoryObjectStore.list()` iterating over its 10,000-key Python dictionary.

> **R2-MC5 (Reader-visible semantics and resolution of VSA choice nodes, update-vs.-delete on purges, post-block remediation, and pre-image pruning):**  
> *"Specify the reader-visible semantics and the resolution protocol for choice nodes, with an explicit rule for update-versus-delete collisions (for example, 'delete wins' for purge branches, or block). Define a pre-image pruning rule and show that Theorem 5.1 holds under it. Describe the remediation path after a block, and measure how many choice nodes remain open under the W2 contention sweep."*

**Response:**  
We closed all five design points in **Sections 3.2, 4.2, 4.5, 5.1, 7.3, and 7.6**:
1. **Reader-visible choice semantics, resolution commit, and protected-branch publish gate (Criterion 2 & Section 4.5):** An open VSA choice node exposes the **fork value** $\rho_0(r, c)$ to queries on an unprotected branch so neither conflicting write is prematurely visible. Any branch marked **protected** (such as `main` by default) enforces a publish gate at catalog CAS time (`OpenChoicesError`) that refuses any snapshot with $\mathcal{V} \neq \emptyset$. Users or agents inspect open choices via `unresolved(T)` and close them via `resolve_choices(T, picks)` (`semlake/maintenance.py`), which commits the chosen values as a standard checked commit before advancing `main`. In the `W2` contention sweep at $\rho = 0.5$ (**Section 7.3**), the 60 merges open **1,509 choice nodes**; `resolve_choices` resolves them in **1.13 ms** median per merge, leaving **0 open choices** so the branch passes the publish gate.
2. **Purge-wins rule for update-vs.-delete conflicts (Criterion 2 & Theorem 5.2):** When a delete commit is marked as a regulatory purge (`purge=True`), a concurrent update to the same row on the partner branch is overridden by the delete (**purge-wins**), and the overridden update is recorded in the merge summary's audit list (`overridden_by_purge`). Thus, a purged row can never remain readable in $T_M$. For unmarked deletes, an update-vs.-delete collision creates a whole-row choice node that is held back from `main` by the publish gate until resolved (`tests/test_revision.py::PurgeWins`).
3. **Post-block remediation path (Section 4.5, "After a block"):** Because Algorithm 2 runs before any data or manifest object is written, a blocked merge writes nothing and moves no branch head. The blocked report branch remediates by rebasing onto the current `main` head (which now already contains the purge in its base snapshot $T_0'$), re-running its aggregation query over the post-purge table, and committing the updated report.
4. **Pre-image pruning and soundness under pruning (Section 4.2, Theorem 5.2, Table 9):** We implemented `prune_preimages(c, K)` and `prunable(repo, c)` in `semlake/maintenance.py`. `prune_preimages(c, K)` strips deleted-row pre-images from commit $c$'s summary, retaining only columns in $K$ and marking the row IDs as `pruned`. In Theorem 5.2, any read predicate that cannot be decided from the kept columns $K$ on a pruned row evaluates to *unknown*, which Algorithm 2 treats as a conflict. Thus pruning can only introduce false blocks and never false negatives. Furthermore, once every active branch head in the catalog has $c$ in its ancestor set (`prunable(repo, c) == True`), no future merge will ever replay $c$ as a post-fork commit, so full pruning ($K = \emptyset$) removes 100% of the erased pre-image values (**cutting summary size by 86% in Table 9**) with zero precision loss.
