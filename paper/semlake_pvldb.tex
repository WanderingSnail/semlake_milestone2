\begin{abstract}
Lakehouse catalogs fork a table in milliseconds by sharing immutable Parquet files, but merging two branches is still decided on files or row identifiers. Such rules abort edits to disjoint rows of one file, or rewrite the file, and they commit silently when one branch deletes or changes rows that the other branch read to compute an aggregate: a regulatory purge and a report over the purged rows touch disjoint files and rows, so the merged snapshot holds both.

We present \systemname, a storage and catalog layer for three-way merging with a stated correctness contract, \emph{purge-safety}: no row a branch read may have been deleted, moved across the read's filter, or changed in a column the read uses by the other branch. Each commit writes a summary with its declared read and delete predicates and the prior values of the rows it changed; a merge decides the contract from summaries alone, and joins and subqueries are projected soundly onto the merged table. The physical merge unions deletion vectors and publishes with one catalog compare-and-swap; we state the commit protocol and five crash-recovery invariants and test them by fault injection at \RecPoints\ crash points (\RecViolations\ violations). On \FullPairs\ pairs of full TPC-H queries against \texttt{lineitem} refreshes, labelled by query results, \systemname\ misses no conflict and blocks \FullSemFBPct\% of the safe pairs (precision \FullSemPrec); a Delta-style file-level read check blocks \FullBoneRFBPct\% (precision \FullBoneRPrec), and row-level merges detect no conflict. A merge of 10K touched files issues \LedSemReq\ object-store requests against \LedBtwoReq\ for copy-on-write, the same as a row-level engine without the check, so the check itself costs no request.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Cloud data lakehouses~\cite{armbrust2020delta, zaharia2021lakehouse, jain2023analyzing, harby2025survey} keep transactional table snapshots over immutable Parquet files on object storage. Dataset versioning systems~\cite{bhattacherjee2015principles, bhardwaj2015datahub, maddox2016decibel, huang2017orpheusdb, wang2018forkbase} and lakehouse catalogs with branches~\cite{tagliabue2024bauplan, icebergbranching, nessie, lakefs, deltaclone} let a pipeline fork a snapshot by copying a metadata pointer, work in isolation, and merge the result back into \texttt{main}. Forking is cheap because files are shared~\cite{bhattacherjee2015principles}; this is the zero-copy cloning that a recent survey of cloud-native databases lists among the metadata optimizations of disaggregated storage~\cite{dong2024cloudnative}. A clone, however, is a one-way operation. Merging two diverged branches has no agreed correctness model, and four patterns recur:
\begin{itemize}[leftmargin=8pt, itemsep=0pt, topsep=1pt]
    \item \textbf{$W_1$ (shared-file disjoint updates):} branches change different rows of the same Parquet files.
    \item \textbf{$W_2$ (hotspot collisions):} branches change the same cells, at contention rate $\rho$.
    \item \textbf{$W_3$ (semantic dependencies):} one branch deletes or changes rows that the other branch read to compute an aggregate or to assert an invariant, and wrote the result elsewhere.
    \item \textbf{$W_4$ (schema evolution and scale):} one branch changes the schema while the other appends, over large manifests and deep commit graphs.
\end{itemize}

Open table formats check conflicts on files or row identifiers, which fails differently on each pattern. File-level optimistic concurrency ($B_1$)~\cite{armbrust2020delta} aborts $W_1$; copy-on-write row merge ($B_2$)~\cite{tagliabue2024bauplan} rewrites every touched file; tuple versioning ($B_3$)~\cite{maddox2016decibel, huang2017orpheusdb} issues requests in proportion to the table. On $W_2$ engines abort the branch or overwrite by last-writer-wins ($B_4$)~\cite{faria2025crdv}. On $W_3$ (Figure~\ref{fig:motivating}) every file-, row- and cell-level rule, including Dolt~\cite{dolt2026}, commits: the purge and the report touch disjoint files and rows. The erasure the purge was meant to perform (for example under GDPR Article~17~\cite{gdpr2016}) is then contradicted by an aggregate in the same published snapshot.

Yilmaz and Dittrich observe that Git branches and MVCC transactions are one concept and propose a generic version control whose \texttt{detect\_conflicts} and \texttt{reconcile} functions are configurable~\cite{yilmaz2025gvc}; they leave both the implementation and an evaluation to future work, and their conflict levels are those of transactions. Verified program merge~\cite{sousa2018verified, zhu2018conflict, zhu2024methodology, dasilva2024detecting, dejesus2024lightweight} works on syntax trees of kilobytes. Predicate and precision locks~\cite{eswaran1976notions, jordan1981precision} and optimistic validation~\cite{kung1981optimistic, larson2011hekaton} test a writer against a reader's predicate, but for short transactions inside one engine. A lakehouse merge has to make that test after two long-lived branches have committed, on object storage, where reading data files costs requests and seconds~\cite{durner2023exploiting}. We measure a merge on four metrics:
\begin{itemize}[leftmargin=8pt, itemsep=0pt, topsep=1pt]
    \item \textbf{$M_1$ (correctness):} recall and precision on $W_3$/$W_4$ conflicts, isolation of $W_2$ collisions, and no false abort on $W_1$.
    \item \textbf{$M_2$ (merge latency):} time that grows with the branch delta, not with the table, reported with its tail.
    \item \textbf{$M_3$ (storage cost):} object-store requests and bytes per commit, merge and compaction.
    \item \textbf{$M_4$ (read overhead):} scan time on a merged snapshot before compaction.
\end{itemize}

\systemname\ rests on three ideas. First, a commit records what a later merge needs: row operations with the prior values of changed rows, schema changes, and the read and delete predicates extracted from its SQL, including a sound single-table projection of joins and subqueries. Second, a merge finds the fork, replays the summaries since it, and checks \emph{purge-safety} with a static test on a conjunctive fragment and, when that cannot decide, an evaluation on the recorded row values, so no data file is read. Third, the physical merge is a union of positional deletion vectors~\cite{okolnychyi2024petabyte, iceberg2025v3} plus one delta file, published by a single catalog compare-and-swap (CAS); same-cell collisions become explicit choice nodes~\cite{zhu2018conflict} that a protected branch refuses until they are resolved.

Our contributions are:
\begin{enumerate}[leftmargin=8pt, itemsep=0pt, topsep=1pt]
    \item \textbf{A merge contract.} Four criteria for $W_1$--$W_4$, with purge-safety proved incomparable to two-branch serializability, and reader-visible semantics for unresolved collisions and for purges that race with updates (Section~\ref{sec:model}).
    \item \textbf{A verifier that reads no data file.} A two-tier predicate check over commit summaries, a projection that makes join and subquery reads checkable, and a pre-image pruning rule under which soundness still holds (Sections~\ref{sec:design}, \ref{sec:correctness}).
    \item \textbf{A commit protocol with recovery invariants.} Ordered writes of uniquely named objects, one CAS, five invariants, garbage collection of orphans, and group commit, tested by fault injection (Section~\ref{sec:design_protocol}).
    \item \textbf{An evaluation against real systems and a result oracle.} lakeFS, Delta Lake on Spark, Dolt and live S3; full TPC-H queries labelled by their results; a per-object cost ledger; scale-up sweeps with P50--P99 latency; and scale-out runs with real threads and a 64-agent simulation in which every system gets the same batching (Section~\ref{sec:eval}).
\end{enumerate}
Section~\ref{sec:bg_novelty} positions \systemname\ against the closest work. The prototype, all raw results and a one-command script that rebuilds every figure and table are public.\footnote{\url{https://github.com/WanderingSnail/semlake_milestone2}}

\section{Background and Positioning}
\label{sec:background}

\subsection{Lakehouse Storage and Deletion Vectors}
\label{sec:bg_lakehouse}

Delta Lake~\cite{armbrust2020delta}, Apache Iceberg~\cite{iceberg2025v3} and Apache Hudi~\cite{jain2023analyzing, sumit2026hudi} layer transactional metadata over immutable Parquet objects~\cite{zaharia2021lakehouse, harby2025survey}. A snapshot points to a manifest tree of data files. Objects cannot be changed in place, so early row-level updates were copy-on-write: changing one record rewrote its whole file~\cite{camacho2024lstbench}. Merge-on-read avoids the rewrite with positional \emph{deletion vectors} (DVs)~\cite{okolnychyi2024petabyte, iceberg2025v3, delta2024rowlevel}: a compressed Roaring bitmap~\cite{lemire2018roaring} per data file marks dead positions, an update sets the old position and appends the new record to a small delta file, readers apply the mask, and compaction later folds DVs into clean files. Iceberg v3 adds stable row lineage identifiers. On object storage the cost of metadata-heavy work is dominated by request count and round trips~\cite{durner2023exploiting}.

\subsection{Workloads and Metrics}
\label{sec:bg_taxonomy}

LST-Bench~\cite{camacho2024lstbench} measures single-branch table operations. A branched pipeline follows \emph{branch, execute, merge}: $T_0 \to (T_A, T_B) \to T_M$. Merging $T_A$ and $T_B$ relative to their fork $T_0$ gives the classes $W_1$--$W_4$ of Section~\ref{sec:intro}, and $M_1$--$M_4$ measure them: $M_1$ is conflict recall and precision on $W_3$/$W_4$, collision isolation on $W_2$ and the false-abort rate on $W_1$; $M_2$ is merge latency over manifest size, history depth, contention and delta size; $M_3$ counts requests and bytes per object class; and $M_4$ is the overhead of DuckDB TPC-H scans~\cite{tpch} on $T_M$ before compaction. Agent workloads~\cite{git4data2026, ang2026branchbench, zhou2026chronos, lyu2026atr} add a fan-in variant, $W_{\text{swarm}}$: $N$ agents fork \texttt{main}, run a mix of $W_1$--$W_3$ tasks and race to publish.

\subsection{What Existing Rules Decide}
\label{sec:bg_what_merges_decide}

Table~\ref{tab:existing_merges} groups existing mechanisms into seven rules. $B_1$ (Iceberg and Delta defaults, lakeFS~\cite{lakefs}) intersects changed file paths: it aborts $W_1$ and tracks no reads. $B_1\text{R}$, Delta's row-level concurrency~\cite{delta2024rowlevel, deltaconcurrency}, resolves $W_1$ writes through DVs but records reads as files and filters, so a report is blocked when any file it scanned changes. $B_2$ merges rows and rewrites each touched file. $B_3$ and $B_4$ rebuild tuple dictionaries or converge by last-writer-wins~\cite{almeida2024crdt}, and neither checks reads. $B_5$ (Dolt) merges cells and validates declared \texttt{FOREIGN KEY} and \texttt{CHECK} constraints, but a query's filter is not a table constraint. $B_6$ (SSI)~\cite{adya1999weak, cahill2008serializable} accepts the serial order ``report, then purge'', which is exactly the outcome a branched publish must reject (Proposition~\ref{prop:serializability}).

Table~\ref{tab:novelty} states what each neighbouring work provides and what it leaves open. The closest is generic version control~\cite{yilmaz2025gvc} (P2), a vision paper: it shows that a commit graph can be read as nested transactions, proposes that conflict detection and reconciliation be pluggable, and lists preferences such as delete-over-update as policies. \systemname\ is a concrete point in that design space, with three differences. \section{Data Model and Merge Contract}
\label{sec:model}

\subsection{Snapshots, Summaries and Branch Deltas}
\label{sec:model_defs}

Let $\mathcal{R}$ be a universe of stable row identifiers (Iceberg v3 row lineage~\cite{iceberg2025v3}) and $\mathcal{A}$ a universe of column names.

\begin{definition}[Snapshot]
A snapshot is $T = (\text{id}, P, S, \rho, \Phi, \mathcal{V})$: an identifier, a tuple $P$ of parent identifiers ($|P| \le 2$), a schema $S$, a partial map $\rho : \mathcal{R} \rightharpoonup (\mathcal{A} \rightharpoonup \mathcal{V}\!\mathit{al})$ from live rows to records, a map $\Phi$ from file identifiers to descriptors (object key, size, DV), and a set $\mathcal{V}$ of open choice nodes.
\end{definition}

A snapshot with two parents is a merge. Snapshots form a DAG; $\text{gen}(u)$ is $0$ for a root and $1 + \max_{p \in P(u)} \text{gen}(p)$ otherwise, and $\text{anc}(u)$ is the set of ancestors of $u$ including $u$. The \emph{fork} of two tips is their common ancestor of highest generation, $T_0 = \text{LCA}(T_A, T_B)$, with ties broken by identifier.

\begin{definition}[Commit Summary and Branch Delta]
Each non-merge commit $c$ records $\delta(c) = (\text{ops}_c, S_c, \Pi_c, \sigma_c)$: $\text{ops}_c$ maps changed rows to \texttt{insert}, \texttt{update} or \texttt{delete} with the assigned values; $S_c$ is the schema; $\Pi_c$ are the commit's predicates; and $\sigma_c$ maps each updated or deleted row to its \emph{pre-image}, the record just before the change. Folding the commits of $\text{anc}(T_B) \setminus \text{anc}(T_0)$ in topological order gives the branch delta $\Delta_B = (\text{ops}_B, D(B), U(B), S_B, \Pi(B), \sigma_B)$ with deleted rows $D(B)$ and updated or inserted rows $U(B)$.
\end{definition}

\subsection{Merge Criteria for $W_1$--$W_4$}
\label{sec:model_predicates}

A merged snapshot $T_M = \text{merge}(T_0, T_A, T_B)$ must satisfy four criteria.

\paragraph{Criterion 1 ($W_1$, convergence).} A row changed by one branch, or identically by both, takes that change. A row updated by both on disjoint columns takes both updates: $\rho_M(r) = \rho_0(r) \oplus \Delta_A(r) \oplus \Delta_B(r)$, whether or not the rows share a file.

\paragraph{Criterion 2 ($W_2$, explicit collisions).} If both branches assign different values to the same cell $(r, c)$, the cell becomes a \emph{choice node} $\texttt{choice}(r, c, [(A, v_A), (B, v_B)]) \in \mathcal{V}_M$, a version-space choice in the sense of Zhu and He~\cite{zhu2018conflict}; the other columns of $r$ still converge. If one branch updates $r$ and the other deletes it, the row becomes a whole-row choice, with one exception that we call \emph{purge-wins}: when the delete belongs to a commit marked as a purge, the delete is applied, the update is dropped, and the merge summary lists the overridden write. A purged row is therefore never readable in $T_M$, whatever the other branch did to it; the delete-over-update preference that P2 names as a policy~\cite{yilmaz2025gvc} is here tied to the erasure contract. The semantics of an open choice are fixed: a reader of $T_M$ sees the \emph{fork} value of the cell (or the fork row, for a whole-row choice), so neither branch's write is visible until someone decides; choices are carried by every descendant snapshot until a commit writes the cell; and a branch declared \emph{protected}, such as \texttt{main}, refuses a head with $\mathcal{V} \neq \emptyset$ (Section~\ref{sec:design_vsa}).

\paragraph{Criterion 3 ($W_3$, predicate preservation).} Table~\ref{tab:predicates} lists the predicate kinds. Unlike a table-wide \texttt{CHECK} constraint ($B_5$), a \texttt{domain} predicate constrains only the values assigned since the fork, so legacy rows outside it do not block a merge.

\paragraph{Criterion 4 ($W_4$, schema compatibility).} Let $\preceq$ be the lossless widening preorder generated by $\texttt{int32} \prec \texttt{int64}$, $\texttt{int32} \prec \texttt{double}$ and $\texttt{float} \prec \texttt{double}$. ($\texttt{int64} \to \texttt{double}$ is excluded: a double represents integers exactly only up to $2^{53}$.) Tip schemas are compatible relative to $S_0$ iff neither branch drops or renames a column of $S_0$, every added column is nullable, and each column's types on both tips widen its fork type; the merged type is their supremum, and no base file is rewritten.

\begin{definition}[Merge Operator]
$\text{merge}(T_0, T_A, T_B)$ returns $\texttt{schema\_conflict}$ if Criterion~4 fails, $\texttt{semantic\_conflict}(V)$ with the violations $V$ if Criterion~3 fails, and otherwise a snapshot $T_M$ with parents $(T_A, T_B)$, rows $\rho_M$, schema $S_M$ and choices $\mathcal{V}_M$ (status \texttt{clean} if $\mathcal{V}_M = \emptyset$, \texttt{vsa} otherwise).
\end{definition}

\subsection{Purge-Safety versus Serializability}
\label{sec:model_invariant}

\begin{definition}[Purge-Safe Merge]
\label{def:purge_safe}
A merge of $T_A, T_B$ with fork $T_0$ is \emph{purge-safe} if, for $(X, Y) \in \{(A, B), (B, A)\}$:
(1)~for every $\texttt{reads\_where}(\varphi_R, C) \in \Pi(Y)$ and $r \in D(X)$, neither the fork value nor the pre-image at delete time satisfies $\varphi_R$: $\rho_0(r) \not\models \varphi_R$ and $\sigma_X(r) \not\models \varphi_R$;
(2)~for every $\texttt{rows\_live}(I)$ or $\texttt{foreign\_key}(I) \in \Pi(Y)$, $D(X) \cap I = \emptyset$;
(3)~for every $\texttt{domain}(\varphi_{\text{dom}}) \in \Pi(Y)$, every value $X$ assigns satisfies $\varphi_{\text{dom}}$;
(4)~for every $\texttt{reads\_where}(\varphi_R, C) \in \Pi(Y)$ and $r \in U(X)$ with tip value $\rho_X(r)$: $\rho_0(r) \models \varphi_R \Leftrightarrow \rho_X(r) \models \varphi_R$ (an inserted row counts as outside $\varphi_R$ at the fork), and if $r$ satisfies $\varphi_R$ then $\rho_0(r)$ and $\rho_X(r)$ agree on $C$.
\end{definition}

\begin{proposition}[Incomparability]
\label{prop:serializability}
Purge-safety and two-branch conflict serializability are incomparable.
\end{proposition}

\begin{proof}
In Figure~\ref{fig:motivating}, $T_B$ reads the rows satisfying $\varphi_R$ and inserts a summary row; $T_A$ deletes rows satisfying $\varphi_D$ and reads nothing of $T_B$. The dependency graph~\cite{adya1999weak} has one antidependency $T_B \xrightarrow{\mathit{rw}} T_A$ and no cycle, so SSI~\cite{cahill2008serializable} accepts the order $T_B \prec T_A$; but $T_M$ holds both the erasure and an aggregate over the erased rows, and Definition~\ref{def:purge_safe} rejects it. Conversely, let both branches set the same cell to different values with no predicates. Definition~\ref{def:purge_safe} holds, yet every serial order loses one write, so a merge that keeps both as a choice is not equivalent to a serial execution.
\end{proof}

The difference is what is published. A serial order explains a history; a merge publishes one snapshot in which both branches' outputs coexist. We enforce the symmetric contract. A one-way variant would check only the pair in which the report follows the purge; we have not built it.

\subsection{Predicate Fragment and Projection}
\label{sec:model_fragment}

The static tier decides clauses in a conjunctive fragment $\mathcal{F}$: $\varphi ::= t_1 \land \dots \land t_m$ where each $t_i$ is $c \;\text{op}\; \ell$ with $\text{op} \in \{=, \neq, <, \le, >, \ge\}$, $c\ \texttt{IN}\ (\ell_1, \dots, \ell_k)$, or $c\ \texttt{BETWEEN}\ \ell_1\ \texttt{AND}\ \ell_2$. Any other single-table clause (\texttt{OR}, \texttt{NOT}, arithmetic, column comparisons) is still \emph{evaluable} on a recorded row, which is all the second tier needs.

A query with joins or subqueries is not a single-table clause. We reduce it to one per query block.

\begin{definition}[Projection of a Read]
\label{def:projection}
Let $Q$ be a query and $R$ the merged table. For each block $b$ of $Q$ that has $R$ in its \texttt{FROM} list through inner joins only, let $\pi_R(b)$ be the block's \texttt{WHERE} and \texttt{ON} condition with every sub-condition that mentions another table, a subquery or an outer reference replaced by \textsc{true}: a conjunct that mentions one disappears, and a disjunction with such a branch becomes \textsc{true} as a whole. A block with an outer, semi or anti join on $R$ has $\pi_R(b) = \textsc{true}$. The projection of $Q$ is the set $\{\texttt{reads\_where}(\pi_R(b), C_Q)\}_b$, where $C_Q$ are the columns of $R$ that $Q$ uses anywhere except inside a conjunct kept unchanged.
\end{definition}

Replacing a condition by \textsc{true} only widens the rows a block may see, so each block's output is a function of the rows of $R$ satisfying $\pi_R(b)$ (Lemma~\ref{lem:projection}). $\pi_R(b)$ is the filter a scan of $R$ would push down; Delta records the same filters as its read predicates and checks them against files, where we check them against rows. One predicate per block, instead of their disjunction, matters for updates: a row that leaves one block's range for another's has crossed a clause.

\subsection{Commit Summaries, Declared Reads and Pruning}
\label{sec:design_summaries}

\paragraph{Summaries.} Finding what changed between two snapshots of an Iceberg or Delta table means reading manifests and often data files. \systemname\ writes one JSON summary per commit: parents and schema; the descriptors of the files whose DV or payload changed; the row operations with assigned values and pre-images; the predicates; and any open choices. Replaying a commit costs one \texttt{GET}, whatever the table size.

\paragraph{Declared reads.} Soundness is a statement about reads the system knows. A commit made through the SQL interface passes each \texttt{SELECT} and \texttt{DELETE} to an extractor built on SQLGlot. A single-table statement yields its \texttt{WHERE} clause and, for a read, the columns used outside it (\texttt{count(*)} uses none, \texttt{SELECT *} all). A join or subquery read is projected block by block (Definition~\ref{def:projection}); a read without a \texttt{WHERE} clause, or one with nothing to keep, is declared as the whole table. A writer that cannot vouch for its reads, for example an external engine that writes through the file interface, commits with \texttt{reads\_captured = false}; a merge then treats that commit as having read the whole table, so every concurrent delete, and every concurrent update or insert, conflicts with it. Undeclared reads thus fail closed. The default can be switched off per merge (\texttt{strict\_reads}), which restores the earlier behaviour and its unsoundness for such writers. A query hook for Spark or dbt that fills the declaration automatically is not built.

\paragraph{Pre-image pruning.} Pre-images are what make the row-value tier possible, and they are also copies of deleted values, which an erasure wants gone. \texttt{prune\_preimages}$(c, K)$ removes from the summary of $c$ the pre-images of the rows $c$ deleted, keeping only the columns $K$, and lists those rows under \texttt{pruned}. A later merge that needs a pruned row treats any read clause it cannot decide from the kept columns as matched. Pruning can therefore add false blocks but cannot hide a conflict (Theorem~\ref{thm:soundness}). Two settings follow. Once every open branch head contains $c$, no future merge replays $c$ against a concurrent reader, and pruning with $K = \emptyset$ is free of any precision cost; this is the rule we recommend for purges. Before that point, $K$ can be set to the columns the open branches filter on. Until a purge is pruned, its summary retains the erased values; Section~\ref{sec:eval_ablation} measures both the bytes and the effect of $K$.

\subsection{Replay Since the Fork}
\label{sec:design_replay}

Branches that merge repeatedly form diamonds in the commit graph. A merge that looks only at the two tip summaries forgets the predicates of earlier merges; one that walks all ancestors replays shared history as false conflicts. Algorithm~1 folds exactly the commits of $\text{anc}(t) \setminus \text{anc}(b)$ for fork $b$: a post-order walk from the tip that stops on entering $\text{anc}(b)$ emits them parents-first; a regular commit costs one summary \texttt{GET} and is folded onto its parent's delta (an update of a row parked in a choice closes the choice; a delete records its pre-image); and at an inner merge with parents $(p_1, p_2)$ and inner fork $f$, the deltas of both parents are stripped of the prefix they share at $f$ and combined, with no further request.

\subsection{Two-Tier Conflict Check}
\label{sec:design_conflict}

Algorithm~2 checks Definition~\ref{def:purge_safe} in both directions.

\paragraph{Tier 1, static.} For a \texttt{deletes\_where}$(\varphi_D)$ of $X$ and a \texttt{reads\_where}$(\varphi_R)$ of $Y$, \texttt{WhereOverlap} decides whether $\varphi_D \land \varphi_R$ is satisfiable when both are in $\mathcal{F}$: per column it intersects the $=$ and \texttt{IN} candidates, removes $\neq$ points and keeps the tightest bounds; an empty column makes the conjunction unsatisfiable. Then no row deleted under $\varphi_D$ satisfied $\varphi_R$ at delete time. One case remains: a row that $X$ updated and then deleted, whose fork value $Y$ may have read, so Line~8 still checks the fork values of those rows.

\paragraph{Tier 2, row values.} When the static test cannot rule an overlap out, because a clause is outside $\mathcal{F}$ or the clauses overlap on values no deleted row has, Lines~9--10 evaluate $\varphi_R$ on each deleted row's fork value and pre-image. Both come from the summaries. Clauses in $\mathcal{F}$ are evaluated natively; other clauses are evaluated by DuckDB~\cite{raasveldt2019duckdb}. Each read clause is evaluated once per set of row versions and the answer is cached, and above \VecThreshold\ rows the evaluation is a single vectorized pass over an Arrow table of the recorded rows instead of a per-row loop. A row whose pre-image is missing or pruned, or a clause that cannot be evaluated, keeps the conflict.

\paragraph{Lineage, keys and domains.} Lines~4--5 intersect each \texttt{rows\_live} and \texttt{foreign\_key} set with $D_X$; Lines~11--13 test each \texttt{domain} predicate on the values $X$ assigned.

\paragraph{Updates and inserts.} Line~14 checks Condition~4: \texttt{Unstable}$(r, p)$ holds when $r$'s membership in $\varphi_R$ differs between its fork and tip values, when $r$ is inside $\varphi_R$ in both and a changed column is in $C$, or when $\varphi_R$ cannot be evaluated on $r$.

\subsection{Reconciliation and Choice Nodes}
\label{sec:design_vsa}

The check runs before any row is materialized, so a $W_3$ or $W_4$ conflict blocks in metadata time and writes nothing. Otherwise rows are reconciled by Criteria~1 and~2, the schemas by Criterion~4, and each same-cell collision becomes a choice node.

A choice is not an error state that halts the repository, as a Dolt conflict table does, and it is not silently decided, as last-writer-wins does. Its life cycle is: (i)~the merged snapshot is written with the choice in its summary and the fork value in the cell; (ii)~the snapshot can become the head of an unprotected branch, where its author or an agent inspects \texttt{unresolved}$(T)$, the list of rows and columns in question; (iii)~\texttt{resolve\_choices}$(T, \mathit{picks})$ closes choices in one ordinary commit, each pick being one branch's option or a new value; (iv)~a protected branch accepts the head only when no choice is open, because the CAS on a protected branch refuses a snapshot with $\mathcal{V} \neq \emptyset$. Since a resolution is a commit, a later merge checks it like any other write. The alternative \texttt{on\_cell\_conflict = abort} returns a write conflict instead, which is what $B_1\text{R}$ does and what the commit service of Section~\ref{sec:design_swarm} uses.

\paragraph{After a block.} A \texttt{semantic\_conflict} names the predicates and rows involved. The blocked reader's remediation is to rebase: fork the current head, re-run the declared query, and commit again, at which point the purge is in its base and no longer concurrent. Nothing has to be undone, because a blocked merge wrote no object and moved no head.

\subsection{Physical Merge, Commit Protocol and Recovery}
\label{sec:design_protocol}
\label{sec:design_physical}

\paragraph{Physical merge.} No base file is rewritten. For every row changed in $T_M$ that lives in base file $f$ at position $\text{pos}_0[r]$, the merge sets that bit: $\text{DV}_M(f) = \text{DV}_A(f) \cup \text{DV}_B(f)$. Inserted and updated records of both branches are written to one delta Parquet file. A merge issues four \texttt{PUT}s: the delta file, the merge summary, a \emph{delta manifest} with the descriptors of the changed files only, and a manifest list naming the base listing and the delta manifests since it. Ordinary commits use the same layout (earlier versions wrote a full listing per commit, which made commit metadata $O(N_{\text{files}})$), and every \ManifestCheckpoint-th commit folds the chain into a new full listing so that reading a snapshot stays a bounded number of \texttt{GET}s.

\paragraph{Commit protocol.} A commit or merge producing snapshot $s$ on branch $\beta$ with expected head $h$ runs:
\begin{enumerate}[leftmargin=12pt, itemsep=0pt, topsep=1pt]
    \item write the data objects of $s$;
    \item write the summary of $s$;
    \item write its delta manifest and manifest list;
    \item $\text{CAS}(\beta, h, s)$ on the catalog.
\end{enumerate}
Every key contains the identifier of $s$, so no write overwrites an object another snapshot uses, and steps 1--3 may be issued concurrently. Step~4 is the commit point. If the CAS fails because $\beta$ moved to $h'$, the writer merges $s$ with $h'$ (a merge is a deterministic function of its parents) and retries with expected head $h'$; if that merge reports a conflict, the commit is rejected with the conflict and nothing is published. Branches isolate writers: a branch reads its own snapshot, and concurrency between branches is resolved only at merge. The catalog is assumed to be a small linearizable store with compare-and-swap, as a transactional catalog or an object store's conditional write provides; in the prototype it is in-process.

\paragraph{Invariants.} The protocol maintains five invariants.
\begin{itemize}[leftmargin=14pt, itemsep=0pt, topsep=1pt]
    \item[\textbf{I1}] \emph{Heads are complete.} A branch head names a snapshot whose summary, manifests and data objects all exist, and so do its ancestors'.
    \item[\textbf{I2}] \emph{Crashes are invisible.} A crash before step~4 changes no head; it leaves only objects no head reaches.
    \item[\textbf{I3}] \emph{Retries are idempotent.} Re-running a crashed commit or merge from the same parents yields a snapshot with the same rows.
    \item[\textbf{I4}] \emph{Batches are atomic.} A group commit moves the head once, so all merges of a batch become visible or none does.
    \item[\textbf{I5}] \emph{Garbage is exactly the unreachable.} Collection deletes an object iff no head, and no in-flight snapshot registered as a root, reaches it.
\end{itemize}
There is no log to replay and nothing to undo: recovery after a crash is to do nothing, and to let garbage collection reclaim the orphans. I1 follows from the write order, I2 from unique keys and the single commit point, I3 from determinism of the merge, I4 from publishing a batch's last snapshot with one CAS, and I5 from computing the reachable set over heads and registered roots before deleting. Section~\ref{sec:eval_correctness} injects a crash before every \texttt{PUT} of commits, merges and batches and checks all five.

\subsection{Commit Service and Group Commit}
\label{sec:design_swarm}

When many writers target one branch, each lost CAS costs another merge. A commit service removes the race: writers hand it their local commits; it takes up to $G$ of them, merges them onto the head one after another in memory, writes the batch's objects together, and publishes the last snapshot with one CAS (I4). A commit that conflicts with the head or with an earlier member of its batch is returned to its writer. Batching is independent of the conflict rule, so in our experiments every baseline receives the same service.

\section{Correctness and Cost Analysis}
\label{sec:correctness}

\subsection{Soundness}
\label{sec:correctness_proofs}

\begin{lemma}[Projection]
\label{lem:projection}
Let $Q$ read table $R$ and let $R'$ differ from $R$ in a set of rows $\Delta$ (deleted, inserted or updated). If, for every predicate $\texttt{reads\_where}(\pi_R(b), C_Q)$ of the projection of $Q$, no row of $\Delta$ satisfies $\pi_R(b)$ before or after the change except rows that satisfy it in both states and agree on $C_Q$, then $Q(R) = Q(R')$.
\end{lemma}

\begin{proof}
Fix a block $b$. Its condition implies $\pi_R(b)$, since $\pi_R(b)$ is obtained by replacing sub-conditions with \textsc{true} under conjunctions and disjunctions only, which are monotone. Hence the block's input from $R$ is contained in $\sigma_{\pi_R(b)}(R)$, and the same for $R'$. A row outside $\pi_R(b)$ in both states contributes to neither. A row inside in both states has, by assumption, the same values on $C_Q$; a kept conjunct that held before still holds, because the row satisfies the conjunction of kept conjuncts in both states, so its truth value is unchanged, and every other use of the row by $Q$ reads only columns of $C_Q$. The block therefore receives the same rows with the same used values, for every block, including blocks under negation or aggregation, whose outputs are functions of their inputs.
\end{proof}

\begin{theorem}[Soundness]
\label{thm:soundness}
Let $T_A, T_B$ have fork $T_0$. Assume (a)~every delete carries a \texttt{deletes\_where} clause its rows satisfied at delete time, (b)~summaries record pre-images, except for rows listed as pruned, and (c)~every read of a commit is declared, or the commit is marked \texttt{reads\_captured = false}. If Algorithm~2 returns $V = \emptyset$ on the deltas of Algorithm~1, the merge is purge-safe (Definition~\ref{def:purge_safe}) for the declared predicates and, for a query $Q$ declared through its projection, $Q$ returns the same result on $T_0$ and on $T_0$ with the other branch's changes applied.
\end{theorem}

\begin{proof}
Condition~2 holds by Lines~4--5 and Condition~3 by Lines~11--13. For Condition~1 fix $\texttt{reads\_where}(\varphi_R) \in \Pi(Y)$ and $r \in D(X)$, deleted under some $\varphi_D$ with $\sigma_X(r) \models \varphi_D$. If \texttt{WhereOverlap} is true, Lines~9--10 established that neither $\rho_0(r)$ nor $\sigma_X(r)$ satisfies $\varphi_R$. If it is false, $\varphi_D \land \varphi_R$ is unsatisfiable, so $\sigma_X(r) \not\models \varphi_R$; and either $\rho_0(r) = \sigma_X(r)$ or $r \in \mathit{moved}_X$ and Line~10 checked $\rho_0(r)$. A pruned row is placed in $\mathit{moved}_X$ and has no complete pre-image, so the evaluator returns \emph{unknown} unless the kept columns decide the clause, and \emph{unknown} is reported as a violation: pruning removes information only in the direction of more violations. Condition~4 holds by Line~14, which flags every changed row that crosses $\varphi_R$, changes $C$ inside it, or cannot be evaluated. A commit with \texttt{reads\_captured = false} contributes $\texttt{reads\_where}(\textsc{true}, \mathcal{A})$, for which Conditions~1 and~4 fail on any change by the other branch, so $V = \emptyset$ implies there was none. The claim about $Q$ is Lemma~\ref{lem:projection} applied to Conditions~1 and~4. Purge-wins cannot violate Condition~1: it only turns an update into the delete that the purge already declared.
\end{proof}

\begin{lemma}[Exact Replay]
\label{lem:replay}
For tip $t$ and fork $b$, Algorithm~1 folds every non-merge commit of $\text{anc}(t) \setminus \text{anc}(b)$ exactly once in topological order, folds no commit of $\text{anc}(b)$, and preserves predicates and open choices across inner merges.
\end{lemma}

\begin{proof}
The post-order walk stops on edges entering $\text{anc}(b)$ and emits a node after its parents outside $\text{anc}(b)$. Stopping on $\text{anc}(b)$, and not on the first-parent chain, keeps commits of branches merged earlier: if a report $R$ forked from $T_0$ is merged with an update branch $U$ into $M_1$, and $M_1$ later meets a purge that forked from $U$, the fork is $U$; $R \in \text{anc}(M_1) \setminus \text{anc}(U)$ is folded and its read predicate survives. At an inner merge, \texttt{StripPrefix} removes the delta shared at the inner fork before combining, so shared history is not counted twice.
\end{proof}

The check is conservative in four ways, which Section~\ref{sec:eval_correctness} quantifies: a projected clause ignores the conditions on other tables; a change inside a clause may leave an aggregate such as \texttt{max} unchanged; a row may enter $\varphi_R$ only on the branch that later deletes it; and pruned pre-images count as matches.

\subsection{Cost}
\label{sec:correctness_complexity}

Let $K$ be the number of non-merge commits since the fork, $\Pi^R$ and $\Pi^D$ the read and delete predicates of both branches, $|\Delta_{\text{rows}}|$ the rows changed and $|\Delta_{\text{files}}|$ the files touched.

\paragraph{Requests.} A merge issues $K$ \texttt{GET}s for summaries, one for the fork summary, one \texttt{LIST} and four \texttt{PUT}s: $K + 6$ requests, independent of $N_{\text{files}}$ and $N_{\text{rows}}$. This is a property of row-level commits with deletion vectors and summaries, not of the semantic check: a row-level engine without the check issues the same requests, and Table~\ref{tab:ledger} shows it.

\paragraph{Time and memory.} The static tier costs $O(|\Pi^D| \cdot |\Pi^R|)$. The row-value tier evaluates each read clause once over the changed rows of the other branch, so the check costs $O(|\Pi^D| \cdot |\Pi^R| + |\Pi^R| \cdot |\Delta_{\text{rows}}|)$ in the worst case; reconciliation and the DV union cost $O(|\Delta_{\text{rows}}| + |\Delta_{\text{files}}|)$. The bound $O(|\Pi_A| \cdot |\Pi_B| + |\Delta_{\text{rows}}|)$ stated in an earlier version assumed a constant number of read predicates per merge. Memory is $O(|\Delta_{\text{rows}}|)$ row versions, because summaries are parsed whole; Section~\ref{sec:eval_scale} sweeps both terms.

\paragraph{Bytes.} A commit that changes $n$ rows in $m$ files writes the new records, a summary of $n$ row operations with pre-images and $m$ descriptors (each carrying a DV), and a delta manifest of $m$ descriptors. Metadata bytes therefore grow with $n$ and $m$ and can exceed the data bytes for narrow updates; write amplification is defined against the bytes of the changed records and reported per object class, with compaction counted (Sections~\ref{sec:eval_cost}, \ref{sec:eval_read}).

\paragraph{Scan overhead.} With $G_{\text{dirty}}$ of $G_{\text{rg}}$ row groups carrying a non-empty DV and a mask factor $\alpha$ on dirty groups, a scan of $T_M$ costs $C_{\text{scan}} (1 + \alpha\, G_{\text{dirty}} / G_{\text{rg}})$; leaving DVs open is cheaper than compacting while the number of scans between merges stays below $C_{\text{compact}} / (\alpha\, C_{\text{scan}}\, G_{\text{dirty}} / G_{\text{rg}})$.

\section{Implementation}
\label{sec:impl}

\systemname\ is a Python prototype of about \EngineLines\ lines (\texttt{metadata}, \texttt{storage}, \texttt{merge}, \texttt{verification}, \texttt{sql\_predicates}, \texttt{maintenance}, \texttt{reader}, \texttt{s3store}, \texttt{baselines}) with about \BenchLines\ lines of benchmarks. Data files are Parquet via \texttt{pyarrow} with a hidden row-identifier column; DVs use \texttt{pyroaring}; SQL is parsed with SQLGlot; scans and non-$\mathcal{F}$ clauses run in DuckDB. Snapshot row state is a copy-on-write overlay over the parent, and each snapshot caches its ancestor generations, so LCA search is a generation-ordered walk that stops below the best common ancestor. \texttt{reader.materialize} rebuilds a snapshot's rows from published objects alone and is the oracle of the recovery tests. The in-memory store and the S3 backend share one interface that counts requests and bytes per object class. \RevTests\ unit tests and a randomized comparison against a brute-force oracle over \FuzzSeeds\ seeds accompany the code.

\paragraph{Lifecycle.} Over \CompMerges\ merges that each delete \CompDeletePct\% of the rows, leaving every DV open rewrites nothing and costs a mean Q6 overhead of \CompLocNone\% for localized and \CompUniNone\% for uniform deletes. Compacting a row group once \CompLocThr\ of it is deleted brings the localized overhead to \CompLocBest\%, but it rewrites \CompLocRewrite\ rows per merge, \CompLocWaf\ rows per deleted row, close to the \CompCowLocWaf\ of copy-on-write, because each merge here deletes more than the threshold inside one group. For uniform deletes the best threshold leaves \CompUniBest\% and rewrites \CompUniWaf\ rows per deleted row against \CompCowUniWaf\ for copy-on-write, which rewrites every touched group at every merge. Deletion vectors therefore do not remove the rewrite; they let it be deferred and batched. Under the dollar model of the artifact (request, storage and CPU prices, 128\,MiB files) and the interval of Table~\ref{tab:scan}, leaving DVs open stays cheaper than rewriting up to \CrossLocRange\ scans per merge for localized deletes and \CrossUniRange\ for uniform ones.

\subsection{Ablations}
\label{sec:eval_ablation}

\input{generated/tab_ablation}

Table~\ref{tab:ablation} switches off one mechanism at a time. The projection, the row-value tier and the update check each remove a class of errors: without the projection, join and subquery reads block almost every refresh; without the row-value tier, clauses outside $\mathcal{F}$ block safe merges; without the update check (Line~14), recall on update and insert pairs falls to \UpdDelOnlyRec. Replaying only the tip commits loses the predicates of branches merged earlier (Lemma~\ref{lem:replay}). Pruning pre-images to the filter columns keeps every decision and cuts the summary by \PruneProjCutPct\%; pruning them entirely cuts \PruneFullCutPct\% and turns a safe report into a block, the direction Theorem~\ref{thm:soundness} allows. The vectorized row-value tier changes time only, and not always for the better: it halves a merge of \VecUpdRows\ updates (\VecUpdS\,s against \LoopUpdS\,s for the per-row loop) and helps deletes checked against \VecPreds\ read clauses (\VecPredsS\,s against \LoopPredsS\,s), but for one clause the loop is faster (\LoopDelS\,s against \VecDelS\,s). Row-level tracking, shared with $B_1\text{R}$, removes the file-packing sensitivity of $B_1$, whose false-abort rate reaches \PackBoneMax\ at \PackMax\ rows per file.

\paragraph{Threads.} Figure~\ref{fig:threads} runs 1 to \ThrMaxWriters\ writer threads against one catalog and a store that sleeps for each request. A writer forks the head, increments one of \ThrRows\ rows in \ThrFiles\ files, declares the read of that row, commits to its branch and publishes. An optimistic client races for the head with a CAS and, when it loses, rebases with a three-way merge and retries; with the commit service it queues, and one committer merges a batch and publishes it with one CAS. Optimistic publishing collapses under contention: \systemname\ peaks at \ThrSemOptPeak\ commits/s with \ThrSemOptPeakWriters\ writers and falls to \ThrSemOptMax\ at \ThrMaxWriters, where a commit loses \ThrSemOptLost\ CAS races and the P99 commit latency is \ThrSemOptTailS\,s; $B_1$ behaves alike (\ThrBoneOptPeak\ and \ThrBoneOptMax). The service removes the races: \systemname\ reaches \ThrSemGrpPeak\ commits/s at \ThrSemGrpPeakWriters\ writers (P99 \ThrSemGrpPeakTailS\,s) and $B_1$ \ThrBoneGrpPeak, so the gain (\ThrSemGrpRatio$\times$) comes from batching and is open to both. Beyond the peak the single committer is the bottleneck: at \ThrMaxWriters\ writers \systemname\ publishes \ThrSemGrpMax\ commits/s and $B_1$ \ThrBoneGrpMax. Requests are scaled down here and CPU time is not, so the Python merge weighs \ThrCpuWeight$\times$ its real share, and \systemname's merge does more CPU work than $B_1$'s path comparison. \section{Related Work}
\label{sec:related}

\paragraph{Version control for data.}
Generic version control~\cite{yilmaz2025gvc} is the closest work and is discussed in Section~\ref{sec:bg_novelty}: it unifies Git and MVCC conceptually and makes conflict detection and reconciliation pluggable, without an implementation; \systemname\ supplies one instance, with a contract outside the transactional isolation levels, for tables on object storage. Dataset versioning~\cite{bhattacherjee2015principles}, DataHub~\cite{bhardwaj2015datahub}, Decibel~\cite{maddox2016decibel}, OrpheusDB~\cite{huang2017orpheusdb} and ForkBase~\cite{wang2018forkbase} study storage layouts for many versions. lakeFS~\cite{lakefs} and Nessie~\cite{nessie} bring Git-like branches to object stores and catalogs and merge by object or table overlap; Iceberg branches and tags~\cite{icebergbranching} and Delta shallow clones~\cite{deltaclone} fork a table but fast-forward or replace a branch, with no three-way merge; Bauplan~\cite{tagliabue2024bauplan} uses branches for write-audit-publish pipelines; Dolt~\cite{dolt2026} merges cells over Prolly trees and validates declared constraints. None of them checks one branch's writes against the other branch's reads.

\paragraph{Lakehouse and cloud-native storage.}
Delta Lake~\cite{armbrust2020delta}, the lakehouse architecture~\cite{zaharia2021lakehouse} and comparative studies~\cite{jain2023analyzing, camacho2024lstbench, harby2025survey} established metadata-driven transactions on object stores; deletion vectors and row lineage~\cite{okolnychyi2024petabyte, iceberg2025v3, delta2024rowlevel} gave them merge-on-read updates, which our physical merge reuses. Hudi~\cite{sumit2026hudi} and Lance~\cite{lance2025} add indexes and multi-modal metadata. The survey of cloud-native databases~\cite{dong2024cloudnative} organizes disaggregated designs and names zero-copy cloning and multi-writer support; Durner et~al.~\cite{durner2023exploiting} give the request-cost model behind our ledger. LakeVilla~\cite{gotz2025lakevilla}, G\"otz et~al.~\cite{gotz2026interoperable} and TreeCat~\cite{oh2025treecat} coordinate multi-table commits and catalog trees. Below the table layer, Velox~\cite{pedreira2022velox} unifies vectorized execution and xNVMe-based I/O~\cite{houlborg2026xnvme} opens new device paths to engines such as DuckDB; both are complementary to merging.

\paragraph{Concurrency control.}
Predicate locks~\cite{eswaran1976notions} and precision locks~\cite{jordan1981precision} test written tuples against readers' predicates, and optimistic schemes~\cite{kung1981optimistic, larson2011hekaton} validate read and scan sets at commit. \systemname\ applies a related test between long-lived branches from stored row values, after both have committed. Adya~\cite{adya1999weak} and Cahill et~al.~\cite{cahill2008serializable} define and enforce serializability under snapshot isolation; Proposition~\ref{prop:serializability} shows why a published merge needs a different contract. CRDTs~\cite{almeida2024crdt, faria2025crdv} converge automatically but neither isolate branches nor check reads.

\paragraph{Program merge.}
Verified three-way merge~\cite{sousa2018verified}, version-space algebra for conflicts~\cite{zhu2018conflict}, structured merge~\cite{zhu2024methodology} and detection of behavioural conflicts by tests or static analysis~\cite{dasilva2024detecting, dejesus2024lightweight} are the program-side counterparts. We keep the three-way formulation and the explicit choice, over row operations and predicates instead of syntax trees.

\paragraph{Agentic workloads.}
Git4Data~\cite{git4data2026} and Chronos~\cite{zhou2026chronos} provide branching for agents, BranchBench~\cite{ang2026branchbench} measures branching under agentic demand, and ATR~\cite{lyu2026atr} revalidates decisions selectively. Our swarm experiments use such workloads.

\section{Limitations and Conclusion}
\label{sec:conclusion}

\emph{Declared reads.} Soundness covers declared reads; the fail-closed default for writers that cannot declare is safe but blocks, and the query hook that would declare reads automatically is not built. \emph{Precision on joins.} A projection keeps only single-table conditions, so \FullWidePct\% of the TPC-H queries are checked as whole-table reads, and precision under the result oracle is \FullSemPrec; predicates that span tables, or re-running a blocked query on the merged data, would raise it. \emph{Scale.} The prototype parses summaries into memory, so a merge is bounded by the rows changed (\SweepMaxRows\ rows in \SweepMaxS\,s here), and its Python merge path costs CPU that grows with the files touched. \emph{Pre-images.} Summaries hold the prior values of changed rows until pruned, about \PreBytesPerRow\ bytes per deleted \texttt{lineitem} row. \emph{Modelled parts.} $B_2$ and $B_6$ are rule models, the 64-agent results are simulated with measured request latencies, the thread experiment scales latencies down, and the catalog is in-process, so I1--I5 are tested against crashes of the writer, not of the catalog. \emph{Single table.} Merges and group commit cover one table; multi-table transactions~\cite{gotz2025lakevilla, gotz2026interoperable} are future work.

\systemname\ gives branch merging on a lakehouse a contract, a check that reads no data file, and a commit protocol with stated recovery invariants. Against a row-level engine it adds no object-store request; what it adds is the decision. On full TPC-H queries labelled by their results it misses no conflict, and it blocks fewer safe merges than a file-level read check, while the storage path it shares with row-level engines keeps a merge at a constant number of requests.
