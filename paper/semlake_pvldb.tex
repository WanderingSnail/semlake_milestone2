\begin{abstract}
While modern cloud data lakehouses enable zero-copy branching for isolated data pipelines, their merge mechanics remain fundamentally brittle. Current systems rely on physical file or row-identifier checks, creating a damaging dichotomy: concurrent modifications to disjoint rows in shared files trigger false conflict aborts and severe copy-on-write amplification, whereas cross-file dependencies---such as data deletions concurrent with aggregate calculations---merge blindly, causing silent semantic corruption. Conversely, verified three-way merge formalisms from software version control operate on abstract syntax trees and cannot scale to petabyte-scale cloud storage without prohibitive I/O and API overhead.

This paper presents \systemname, a lakehouse storage and catalog architecture that establishes predicate-level three-way semantic merging over table snapshots without rewriting base columnar files. \systemname\ formalizes a purge-safe merge invariant that decouples semantic conflict verification from physical data reconciliation, verifying branch compatibility at metadata time with complexity proportional only to branch delta size. Our investigation yields four key insights: (1)~predicate-level verification completely eliminates silent semantic corruption across dependent queries and deletes, capturing subtle integrity violations that escape both file- and row-level engines; (2)~decoupling row updates from file boundaries eliminates false write conflicts, achieving near-optimal write amplification during concurrent updates; (3)~metadata-driven conflict checking keeps the number of object-store requests per merge independent of table size, about three orders of magnitude fewer than copy-on-write merging; and (4)~when extended beyond standard data pipelines to high-concurrency autonomous agent swarms, this semantic merge model resolves severe branch fan-in contention without human intervention. \systemname\ demonstrates that semantic branch merging can be achieved at cloud scale, bridging the gap between database consistency and zero-copy dataset versioning.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Cloud data lakehouses~\cite{armbrust2020delta, zaharia2021lakehouse, jain2023analyzing, harby2025survey} decouple compute engines from cloud object storage (such as AWS S3) and expose transactional table snapshots over immutable Parquet files. To isolate data engineering jobs, write-audit-publish (WAP) quality gates, regulatory data scrubs, and collaborative analytics, dataset versioning systems~\cite{bhattacherjee2015principles, bhardwaj2015datahub, maddox2016decibel, huang2017orpheusdb, wang2018forkbase} and zero-copy lakehouse catalogs~\cite{tagliabue2024bauplan, gotz2025lakevilla, gotz2026interoperable, oh2025treecat} allow users to fork a table snapshot in milliseconds by copying a metadata pointer, execute transformations on an isolated branch, and merge the verified branch back into \texttt{main}.

Creating a branch on cloud object storage is cheap because immutable Parquet files are shared across snapshots~\cite{bhattacherjee2015principles}. Merging two diverged table branches, however, lacks a sound correctness model at lakehouse scale. In production data lakehouses, concurrent branches interact across four fundamental workload patterns:
\begin{itemize}[leftmargin=8pt, itemsep=0pt, topsep=1pt]
    \item \textbf{$W_1$ (Shared-file disjoint updates):} Branches update/delete non-overlapping rows in the same multi-hundred-megabyte Parquet files.
    \item \textbf{$W_2$ (Hotspot key collisions):} Branches concurrently modify overlapping keys under varying contention density $\rho$, requiring structured isolation without abort storms.
    \item \textbf{$W_3$ (Semantic dependencies):} One branch deletes/modifies rows (e.g., regulatory purge) that a concurrent branch read to compute an aggregate or assert an invariant, writing output to a disjoint file.
    \item \textbf{$W_4$ (Schema evolution and manifest scale):} One branch evolves schema while a concurrent branch appends data across deep manifests and multi-hop DAGs.
\end{itemize}

State-of-the-art open table formats and versioned databases evaluate conflicts solely at physical file granularity or row-identifier granularity, failing across $W_1$--$W_4$. Under file-level optimistic concurrency control ($B_1$)~\cite{armbrust2020delta}, $W_1$ triggers false conflict aborts, while copy-on-write row merge ($B_2$)~\cite{tagliabue2024bauplan} and tuple-dictionary versioning ($B_3$)~\cite{maddox2016decibel, huang2017orpheusdb} incur severe write amplification or $O(N_{\text{files}})$ S3 requests on $W_4$. On $W_2$, existing engines either abort the entire branch ($B_1$--$B_3$) or silently overwrite colliding cells via last-writer-wins CRDTs ($B_4$)~\cite{faria2025crdv}. Worse, as shown in Figure~\ref{fig:motivating}, all file-, row-, and cell-level engines ($B_1$--$B_4$, Dolt~\cite{dolt2026}) fail on $W_3$: when a compliance branch $T_A$ purges VIP records in a base file while an analytics branch $T_B$ aggregates revenue over those same records into a new summary file, the modified file sets and row IDs are disjoint, causing existing systems to commit a corrupted snapshot.

In the programming-languages (PL) community, three-way structured and semantic merges have been formalized using verification conditions~\cite{sousa2018verified}, version-space algebras~\cite{zhu2018conflict}, AST matching~\cite{zhu2024methodology}, and post-merge static analysis or unit testing~\cite{dasilva2024detecting, dejesus2024lightweight}. However, PL techniques operate on abstract syntax trees measured in kilobytes. Lakehouse tables span billions of rows across thousands of cloud objects, where scanning data files at merge time incurs prohibitive S3 API latencies and byte transfer charges~\cite{durner2023exploiting}. Thus, a lakehouse merge engine must satisfy four core system objectives, which serve as our unified evaluation metrics across $W_1$--$W_4$:
\begin{itemize}[leftmargin=8pt, itemsep=0pt, topsep=1pt]
    \item \textbf{$M_1$ (Semantic correctness on $W_1$--$W_4$):} 100\% recall on cross-branch semantic ($W_3$) and schema ($W_4$) conflicts, hotspot collision isolation ($W_2$), and 0\% false aborts on shared files ($W_1$).
    \item \textbf{$M_2$ (Sub-second merge latency on $W_2, W_4$):} Scale three-way diff and commit latency with branch delta size rather than total file count ($W_4$), DAG depth ($W_4$), or contention $\rho$ ($W_2$).
    \item \textbf{$M_3$ (Cloud cost efficiency on $W_1, W_4$):} Bound S3 API calls to $O(\Delta_{\text{manifest}})$ and maintain $\text{WAF} \approx 1$ without full-file CoW rewrites.
    \item \textbf{$M_4$ (Bounded post-merge read overhead on $W_1$):} Preserve high-throughput analytical scans over merged snapshots prior to compaction.
\end{itemize}

To meet $M_1$--$M_4$ simultaneously, we present \systemname, a lakehouse storage and catalog architecture built upon three technical pillars. First, for \emph{zero-copy physical reconciliation} ($W_1, W_4 \to M_3, M_4$), \systemname\ grounds row updates on positional Roaring deletion vectors (DVs)~\cite{okolnychyi2024petabyte, iceberg2025v3} and incremental delta manifests, compiling concurrent shared-file updates into bitwise bitmap unions and a single delta Parquet append. Second, for \emph{metadata-time semantic and schema verification} ($W_3, W_4 \to M_1, M_2$), each commit writes a compact JSON summary capturing row operations, schema changes, delete-time pre-images, and SQL predicates extracted from \texttt{SELECT} and \texttt{DELETE} statements. At merge time, \systemname\ locates the lowest common ancestor (LCA) via generation-pruned search, replays non-merge commits since the fork, checks static predicate satisfiability in metadata time, and, when the static test cannot rule out an overlap, checks the deleted rows' values at the fork and at delete time. Third, for \emph{structured conflict isolation} ($W_2 \to M_1, M_2$), true cell collisions are preserved in VSA choice nodes~\cite{zhu2018conflict} in catalog metadata rather than triggering abort storms.

Finally, beyond standard lakehouse pipelines, we evaluate \systemname\ on an application extension: high-concurrency autonomous agent swarms ($W_{\text{swarm}}$)~\cite{git4data2026, ang2026branchbench, zhou2026chronos, lyu2026atr}. When $N$ AI agents concurrently fork a shared table, execute a composite mix of $W_1, W_2,$ and $W_3$ operations, and race to advance \texttt{main} via catalog compare-and-swap (CAS), \systemname\ turns lost CAS races into fast server-side semantic merges with group commit, satisfying $M_1$--$M_3$ under extreme branch fan-in.

In summary, this paper makes five contributions:
\begin{enumerate}[leftmargin=8pt, itemsep=0pt, topsep=1pt]
    \item \textbf{Unified Three-Way Merge Model:} We formalize four criteria for $W_1$--$W_4$---disjoint convergence ($W_1$), VSA hotspot isolation ($W_2$), purge-safe merging ($W_3$), and schema subtyping ($W_4$)---and show that purge-safety and two-branch serializability ($B_6$) are incomparable (Section~\ref{sec:model}).
    \item \textbf{Two-Tier Predicate Verifier:} A metadata-time static overlap analyzer paired with a check of the deleted rows' recorded values that clears false conflicts without sacrificing recall (Section~\ref{sec:design}).
    \item \textbf{DAG Replay and Bounds ($M_1$--$M_4$):} An exact replay-since-fork algorithm over diamond commit DAGs with Roaring DV reconciliation, backed by formal correctness ($M_1$), latency ($M_2$), S3 API cost ($M_3$), and post-merge scan overhead ($M_4$) bounds (Sections~\ref{sec:design}, \ref{sec:correctness}).
    \item \textbf{System Implementation:} We implement \systemname\ over Parquet, Roaring bitmaps, DuckDB, and SQLGlot, with request counting under an S3 price and latency model, and a comparison against the Dolt binary (Section~\ref{sec:impl}).
    \item \textbf{Comprehensive Evaluation:} We evaluate \systemname\ across $W_1$--$W_4$, TPC-H refresh pairs, and the $W_{\text{swarm}}$ agent extension against $B_1$--$B_6$ along metrics $M_1$--$M_4$ (Section~\ref{sec:eval}).
\end{enumerate}

\section{Background and Motivation}
\label{sec:background}

\subsection{Lakehouse Storage, Deletion Vectors, and Cloud Costs}
\label{sec:bg_lakehouse}

Open lakehouse table formats such as Delta Lake~\cite{armbrust2020delta}, Apache Iceberg~\cite{iceberg2025v3}, and Apache Hudi~\cite{jain2023analyzing, sumit2026hudi} layer transactional metadata over immutable columnar Parquet files on cloud object stores~\cite{zaharia2021lakehouse, harby2025survey}. A table state is defined by an immutable snapshot pointing to a manifest tree of data files. Because S3 objects cannot be modified in place, early lakehouse deployments implemented row-level \texttt{UPDATE} and \texttt{DELETE} operations via copy-on-write (CoW): modifying a single record inside a 512\,MB Parquet file required reading the entire file and writing a new 512\,MB copy~\cite{camacho2024lstbench}, resulting in extreme write amplification ($\text{WAF} \gg 1$).

As Durner et~al.~\cite{durner2023exploiting} demonstrate, cloud object storage performance and billing for metadata-intensive operations are governed by API request latencies (30\,ms to 100\,ms per call) and per-request pricing (\$0.005 per 1,000 \texttt{PUT}/\texttt{LIST} calls and \$0.0004 per 1,000 \texttt{GET} calls) rather than raw bandwidth. To avoid full-file rewrites, Okolnychyi et~al.~\cite{okolnychyi2024petabyte}, the Apache Iceberg v3 specification~\cite{iceberg2025v3}, and Delta Lake deletion vectors~\cite{delta2024rowlevel} adopt merge-on-read (MoR) with positional deletion vectors (DVs). A DV is a compressed Roaring bitmap associated with a base Parquet file that marks the zero-based positions of deleted or superseded rows. An update sets the old row position in the base file's DV and appends the updated record to a small delta Parquet file. Analytical readers apply the bitmap mask during scans, and background compaction periodically folds DVs back into clean base files. Iceberg v3 further assigns stable row lineage identifiers so logical row identity is preserved across updates.

\subsection{Problem Taxonomy ($W_1$--$W_4$) and Design Metrics ($M_1$--$M_4$)}
\label{sec:bg_taxonomy}

While prior work benchmarked single-branch table operations in LST-Bench~\cite{camacho2024lstbench}, multi-branch development introduces the \emph{Branch-Execute-Merge} lifecycle: $T_0 \xrightarrow{\text{Branch}} (T_A, T_B) \xrightarrow{\text{Execute}} (T_A', T_B') \xrightarrow{\text{Merge}} T_M$. When two diverged branches $T_A$ and $T_B$ merge relative to their lowest common ancestor $T_0$, four canonical workload interaction classes arise:
\begin{enumerate}[leftmargin=8pt, itemsep=0pt, topsep=1pt]
    \item \textbf{Shared-File Disjoint Updates ($W_1$):} Concurrent branches modify distinct row IDs ($W(A) \cap W(B) = \emptyset$) or disjoint columns co-residing in shared Parquet files, requiring 0\% false aborts ($M_1$), $\text{WAF} \approx 1$ ($M_3$), and $<8\%$ localized scan overhead ($M_4$).
    \item \textbf{Hotspot Key Collisions ($W_2$):} Concurrent branches update overlapping keys with contention density $\rho \in (0, 1]$, requiring cell collision isolation ($M_1$) without whole-branch abort storms ($M_2$).
    \item \textbf{Semantic Dependencies ($W_3$):} Branch $A$ purges rows satisfying $\varphi_D$ while Branch $B$ reads rows satisfying $\varphi_R$ to materialize a summary or assert an invariant ($M_1: \Delta_A \not\models \Pi_B$).
    \item \textbf{Schema Evolution and Manifest Scale ($W_4$):} Branch $A$ evolves schema $S_0 \to S_A$ while Branch $B$ appends data files across $N_{\text{files}}$ base files and multi-hop DAGs ($M_1, M_2, M_3$).
\end{enumerate}

These four workloads directly ground our four evaluation metrics:
\begin{itemize}[leftmargin=8pt, itemsep=0pt, topsep=1pt]
    \item \textbf{$M_1$ (Semantic Correctness on $W_1$--$W_4$):} Recall and precision on $W_3, W_4$~\cite{sousa2018verified, dasilva2024detecting}, cell collision isolation on $W_2$, and false-abort rate (FAR) on $W_1$.
    \item \textbf{$M_2$ (Merge Latency on $W_2, W_4$):} Wall-clock three-way diff and commit latency across manifest depth ($W_4$), DAG history depth ($W_4$), and contention density $\rho$ ($W_2$)~\cite{jain2023analyzing, oh2025treecat}.
    \item \textbf{$M_3$ (Cloud Cost Efficiency on $W_1, W_4$):} S3 API requests, dollar cost under the Durner et~al.\ model~\cite{durner2023exploiting}, and write amplification factor (WAF).
    \item \textbf{$M_4$ (Post-Merge Scan Penalty on $W_1$):} Relative query latency overhead on merged snapshots $T_M$ before compaction in DuckDB TPC-H scans~\cite{camacho2024lstbench, tpch}.
\end{itemize}

\subsection{Why Existing Merge Mechanisms Fail ($B_1$--$B_6$ and $B_1\text{R}$)}
\label{sec:bg_what_merges_decide}

Prior art brackets the lakehouse merge problem from two directions: dataset versioning systems~\cite{bhattacherjee2015principles, bhardwaj2015datahub, maddox2016decibel, huang2017orpheusdb, wang2018forkbase, tagliabue2024bauplan} provide scalable branching without semantic merge verification, whereas program-merge verifiers~\cite{sousa2018verified, zhu2018conflict, zhu2024methodology, dasilva2024detecting, dejesus2024lightweight} provide three-way guarantees over kilobyte-scale ASTs that cannot scan billion-row S3 tables.

To establish a unified baseline taxonomy across the paper, we categorize existing mechanisms into six baseline families ($B_1$--$B_6$, plus $B_1\text{R}$ as the row-level write variant of $B_1$): $B_1$--$B_4$ and $B_1\text{R}$ represent lakehouse and dataset-versioning architectures, $B_5$ (Dolt~\cite{dolt2026}) represents an external constraint-aware cell-merge engine, and $B_6$ (Serializable Snapshot Isolation, SSI~\cite{cahill2008serializable}) represents classical OLTP concurrency control. Table~\ref{tab:existing_merges} summarizes their behavior across $W_1$--$W_4$ and $M_1$--$M_4$:
\begin{itemize}[leftmargin=8pt, itemsep=0pt, topsep=1pt]
    \item \textbf{$B_1$: Native file-level OCC (Iceberg/Delta default)}~\cite{armbrust2020delta} intersects modified file paths since $T_0$, causing 100\% false aborts on shared-file updates ($W_1$), abort storms on $W_2$, $O(N_{\text{files}})$ manifest scans on $W_4$, and 0\% recall on semantic dependencies ($W_3$).
    \item \textbf{$B_1\text{R}$: Delta row-concurrency variant of $B_1$}~\cite{delta2024rowlevel} resolves $W_1$ writes via DVs but tracks reads at file granularity (\texttt{Concurrent\allowbreak Delete\allowbreak Read\allowbreak Exception}), false-blocking queries when any row in a scanned file is deleted ($W_3$).
    \item \textbf{$B_2$: Copy-on-Write row merge (Bauplan/lakeFS)}~\cite{tagliabue2024bauplan} resolves row IDs on $W_1$ with 0\% read penalty ($M_4$), but rewrites entire files on every merge ($M_3: \text{WAF} \gg 1$), aborts whole branches on $W_2$, and scores 0\% recall on $W_3$.
    \item \textbf{$B_3$: Relational tuple versioning (Decibel/OrpheusDB)}~\cite{maddox2016decibel, huang2017orpheusdb} tracks per-tuple bitmaps in local DBMS storage; rebuilding per-file dictionaries on cloud lakehouses incurs $O(N_{\text{files}})$ S3 calls ($M_2, M_3$) and misses read predicates on $W_3$.
    \item \textbf{$B_4$: Automatic CRDT views (CRDV)}~\cite{faria2025crdv, almeida2024crdt} guarantees state convergence via last-writer-wins, overwriting updates on $W_2$ and admitting semantic violations on $W_3$ without audit gates.
    \item \textbf{$B_5$: Constraint-aware cell merge (Dolt)}~\cite{dolt2026} merges Prolly trees at cell granularity and validates declared \texttt{FOREIGN KEY} and \texttt{CHECK} constraints, but misses query read predicates ($W_3$) and rejects \texttt{ALTER TABLE ADD CONSTRAINT CHECK} when legacy $T_0$ rows violate the new bound.
    \item \textbf{$B_6$: Classical Serializable Snapshot Isolation (SSI)}~\cite{eswaran1976notions, adya1999weak, cahill2008serializable} tracks antidependencies in volatile lock tables for online OLTP, permitting the one-way schedule $T_B \prec T_A$ which violates purge-safety when merged into a single published snapshot $T_M$ (Proposition~\ref{prop:serializability}).
\end{itemize}

\subsection{Extension Beyond Lakehouse Pipelines: Concurrent Agent Workloads ($W_{\text{swarm}}$)}
\label{sec:bg_swarms}

While three-way semantic merge is primarily designed for lakehouse ETL, backfill, and WAP pipelines ($W_1$--$W_4$), emerging autonomous agent workflows (e.g., Git4Data~\cite{git4data2026}, Chronos~\cite{zhou2026chronos}, BranchBench~\cite{ang2026branchbench}, ATR~\cite{lyu2026atr}) extend database branching to multi-agent swarms. Under high concurrency, git-style data branching faces severe merge bottlenecks. We define \textbf{$W_{\text{swarm}}$} as a composite fan-in workload where $N \in [8, 64]$ autonomous agents concurrently fork from \texttt{main}, execute mixed SQL operations combining $W_1$ (disjoint row updates), $W_2$ (hotspot key updates), and $W_3$ (range deletes vs.\ aggregate queries), and race to publish via catalog CAS. Under $B_1$ or $B_1\text{R}$, losing agents suffer abort storms or false read blocks. Extending \systemname\ with a server-side CAS merge service and group commit turns lost CAS races into metadata-time semantic merges, optimizing $M_1$ (zero committed hazards), $M_2$ (high throughput), and $M_3$ (low WAF) under extreme fan-in.

\section{Formal Data Model and Three-Way Merge Invariants}
\label{sec:model}

We now formalize the lakehouse snapshot model, branch deltas, and the four unified three-way merge criteria that govern $W_1$--$W_4$ in one-to-one correspondence.

\subsection{Snapshot DAG, Commit Summaries, and Branch Deltas}
\label{sec:model_defs}

Let $\mathcal{R}$ be a universe of stable row identifiers (matching Iceberg v3 row lineage IDs~\cite{iceberg2025v3}) and $\mathcal{A}$ be a universe of column names.

\begin{definition}[Table Snapshot]
A table snapshot is a tuple $T = (\text{id}, P, S, \rho, \Phi)$, where $\text{id}$ is a unique snapshot identifier, $P \subseteq \text{id}^*$ is a tuple of parent snapshot identifiers ($|P| \in \{0, 1, 2\}$), $S = (a_1 : \tau_1, \dots, a_k : \tau_k)$ is the table schema, $\rho : \mathcal{R} \rightharpoonup (\mathcal{A} \rightharpoonup \mathcal{V})$ is a partial map from live row IDs to column-value records, and $\Phi$ is a map from file identifiers to physical file descriptors $(k_{\text{obj}}, \text{size}, \text{token}, \text{DV})$.
\end{definition}

A snapshot with $|P| = 1$ is a regular commit; a snapshot with $|P| = 2$ is a merge commit. The snapshots of a repository form a directed acyclic graph (DAG) $G = (V, E)$ with edges $(u, p)$ for each $p \in P(u)$. Each snapshot $u$ has a generation number $\text{gen}(u)$, defined as $0$ if $P(u) = \emptyset$ and $1 + \max_{p \in P(u)} \text{gen}(p)$ otherwise. Let $\text{anc}(u)$ denote the set of all ancestors of $u$ (including $u$ itself).

\begin{definition}[Fork Point]
Given two branch tips $T_A$ and $T_B$, their fork point is the shared ancestor of maximum generation: $T_0 = \text{LCA}(T_A, T_B) = \arg\max_{u \in \text{anc}(T_A) \cap \text{anc}(T_B)} \text{gen}(u)$, breaking ties deterministically by snapshot identifier.
\end{definition}

\begin{definition}[Commit Summary and Folded Branch Delta]
Each non-merge commit $c$ records a delta summary $\delta(c) = (\text{ops}_c, S_c, \Pi_c, \sigma_c)$, where $\text{ops}_c : \mathcal{R} \rightharpoonup \{\texttt{insert}, \texttt{update}, \texttt{delete}\} \times (\mathcal{A} \rightharpoonup \mathcal{V})$ maps modified row IDs to operation kinds and column values; $S_c$ is the schema; $\Pi_c$ is a tuple of attached semantic predicates; and $\sigma_c : \mathcal{R} \rightharpoonup (\mathcal{A} \rightharpoonup \mathcal{V})$ maps deleted rows to their pre-images immediately before deletion. For branch tip $T_B$ and fork $T_0$, let $\mathcal{C}(T_0, T_B) = \{c \in \text{anc}(T_B) \setminus \text{anc}(T_0)\}$. Folding $\mathcal{C}(T_0, T_B)$ in topological order yields the folded branch delta $\Delta_B = (W(B), D(B), S_B, \Pi(B))$, comprising write set $W(B) = (\text{ops}_B, \sigma_B)$, deleted row set $D(B) = \{r \mid \text{ops}_B(r) = (\texttt{delete}, \cdot)\}$, tip schema $S_B$, and predicates $\Pi(B)$.
\end{definition}

\subsection{Unified Three-Way Merge Criteria Across $W_1$--$W_4$}
\label{sec:model_predicates}

A valid merged snapshot $T_M = \text{merge}(T_0, T_A, T_B)$ must simultaneously satisfy four formal criteria corresponding one-to-one with $W_1$--$W_4$:

\paragraph{Criterion 1 ($W_1$: Disjoint Row and Column Convergence).}
For each row ID $r \in \mathcal{R}$ modified in $\text{ops}_A \cup \text{ops}_B$: if $r$ is modified by only one branch $X \in \{A, B\}$ or modified identically by both ($\text{ops}_A(r) = \text{ops}_B(r)$), $\rho_M(r)$ adopts $\text{ops}_X(r)$ directly; if both branches update $r$ on disjoint column subsets ($\text{cols}_A(r) \cap \text{cols}_B(r) = \emptyset$), the updates commute and converge into $\rho_M(r) = \rho_0(r) \oplus \Delta_A(r) \oplus \Delta_B(r)$ regardless of physical file co-location.

\paragraph{Criterion 2 ($W_2$: Hotspot Cell-Collision Isolation via VSA).}
If both branches assign distinct values $v_A \neq v_B$ to the same column $c \in \text{cols}_A(r) \cap \text{cols}_B(r)$ or one updates $r$ while the other deletes $r$, the conflicting cell is encapsulated without data loss into a Version Space Algebra (VSA)~\cite{zhu2018conflict} choice node $\texttt{choice}(r, c, [(A, v_A), (B, v_B)]) \in \mathcal{V}_M$, while non-conflicting columns of $r$ still converge in $\rho_M(r)$.

\paragraph{Criterion 3 ($W_3$: Cross-Branch Predicate Preservation).}
Table~\ref{tab:predicates} defines the five predicate kinds in \systemname: \texttt{reads\_where}$(\varphi_R)$ and \texttt{deletes\_where}$(\varphi_D)$ capture the selection scope of SQL \texttt{SELECT} and \texttt{DELETE} statements; \texttt{rows\_live}$(I)$ and \texttt{foreign\_key}$(I)$ specify finite row-ID sets $I \subset \mathcal{R}$ that must remain live in $T_M$; and \texttt{domain}$(\varphi_{\text{dom}})$ asserts a value invariant over concurrent writes $\text{ops}_X$. Unlike a table-wide SQL \texttt{CHECK} constraint in $B_5$ (Dolt), a \texttt{domain} predicate validates only the new assignments in $\text{ops}_X$ since $T_0$ and does not fail if untouched legacy records in $T_0$ lie outside $\varphi_{\text{dom}}$.

\paragraph{Criterion 4 ($W_4$: Bidirectional Schema Subtyping Compatibility).}
Let $\preceq_{\text{type}}$ denote the lossless numeric widening preorder ($\texttt{int32} \prec_{\text{type}} \texttt{int64} \prec_{\text{type}} \texttt{double}$, and $\tau \preceq_{\text{type}} \tau$ for all types $\tau$). Tip schemas $S_A$ and $S_B$ are merge-compatible relative to $S_0$ iff for every column $a \in \mathcal{A}$: (a)~neither branch drops or renames a column present in $S_0$; (b)~any column $a \notin S_0$ added by $S_A$ or $S_B$ is nullable (and if added by both, has a common supertype); and (c)~for every $a \in S_0$, $\tau_0(a) \preceq_{\text{type}} \tau_A(a)$ and $\tau_0(a) \preceq_{\text{type}} \tau_B(a)$, yielding the unified schema $S_M(a) = \sup_{\preceq_{\text{type}}}(\tau_A(a), \tau_B(a))$ without rewriting base Parquet files.

\begin{definition}[Three-Way Table Merge Operator]
A three-way merge operator $\text{merge}(T_0, T_A, T_B)$ evaluates Criteria~1--4 across $W_1$--$W_4$: (1)~If Criteria~3 and~4 hold, it returns merged snapshot $T_M$ with parents $(T_A, T_B)$, converged row state $\rho_M$ ($W_1$, status $\texttt{clean}$, outcome \texttt{keep} when $\mathcal{V}_M = \emptyset$), VSA choices $\mathcal{V}_M$ ($W_2$, status $\texttt{vsa}$, outcome \texttt{replan} when $\mathcal{V}_M \neq \emptyset$), and unified schema $S_M$ ($W_4$); (2)~$\texttt{semantic\_conflict}(V)$ (\texttt{block}) if predicate violations $V \neq \emptyset$ violate Criterion~3 ($W_3$); or (3)~$\texttt{schema\_conflict}$ (\texttt{block}) if schemas violate Criterion~4 ($W_4$).
\end{definition}

\subsection{Purge-Safe Merge Invariant vs.\ Classical Serializability ($W_3$ vs.\ $B_6$)}
\label{sec:model_invariant}

We now formalize Criterion~3 ($W_3$) as the \emph{purge-safe merge invariant} and prove its relationship to classical transaction serializability ($B_6$, SSI)~\cite{eswaran1976notions, adya1999weak, cahill2008serializable}.

\begin{definition}[Purge-Safe Merge]
\label{def:purge_safe}
Let $T_A, T_B$ be branches with fork $T_0$. A merge $T_M = \text{merge}(T_0, T_A, T_B)$ is \emph{purge-safe} if, symmetrically for $(X, Y) \in \{(A, B), (B, A)\}$: (1)~for every $\texttt{reads\_where}(\varphi_R) \in \Pi(Y)$ and every row $r \in D(X)$, neither the row's value at the fork nor its pre-image at delete time satisfies $\varphi_R$: $\rho_0(r) \not\models \varphi_R$ (when $r$ exists in $T_0$) and $\sigma_X(r) \not\models \varphi_R$; (2)~for every $\texttt{rows\_live}(I)$ or $\texttt{foreign\_key}(I) \in \Pi(Y)$, $D(X) \cap I = \emptyset$; and (3)~for every $\texttt{domain}(\varphi_{\text{dom}}) \in \Pi(Y)$ and $(r, v) \in \text{ops}_X$, $v \models \varphi_{\text{dom}}$.
\end{definition}

\begin{proposition}[Purge-Safety vs.\ Serializability ($B_6$)]
\label{prop:serializability}
Purge-safety and two-branch conflict serializability are incomparable. There exist branch pairs $(T_A, T_B)$ that admit a serializable execution order $T_B \prec T_A$ under SSI ($B_6$)~\cite{cahill2008serializable} yet violate purge-safety, and purge-safe merges that are not serializable.
\end{proposition}

\begin{proof}
Consider Figure~\ref{fig:motivating}. Branch $T_B$ reads rows satisfying $\varphi_R = (\texttt{kind='vip'} \land \texttt{val}\ge 10)$ from $T_0$ and inserts a summary row into a new file. Branch $T_A$ deletes rows satisfying $\varphi_D = (\texttt{kind='vip'})$ from $T_0$ and reads nothing from $T_B$. In Adya's dependency graph~\cite{adya1999weak}, there is a single antidependency $T_B \xrightarrow{\mathit{rw}} T_A$ and no edge $T_A \to T_B$. Because a cycle requires two consecutive $\mathit{rw}$-edges~\cite{cahill2008serializable}, the graph is acyclic and the serial schedule $T_B \prec T_A$ is accepted by SSI. However, in $T_M$, both the erasure of VIP records and the derived summary coexist in the same published snapshot. Because the deleted VIP rows satisfy $\varphi_R$, Definition~\ref{def:purge_safe} rejects the merge. Conversely, let both branches update the same cell of the same row to different values, with no predicates. Definition~\ref{def:purge_safe} holds trivially, but any serial order loses one of the two writes, so a merge that keeps both outcomes as a VSA choice (Criterion~2) is not equivalent to a serial execution. Hence neither property implies the other.
\end{proof}

In a branched lakehouse, $T_M$ is published as a single coherent dataset snapshot: if $T_A$ is a regulatory GDPR erasure or a data-cleaning scrub of corrupted records, allowing $T_B$'s pre-purge aggregate into $T_M$ means the published table simultaneously claims the records were erased while publishing statistics derived from them. When an application instead desires directional serializability (accepting $T_B \prec T_A$), \systemname\ supports an optional directional mode; by default, it enforces symmetric purge-safety.

\subsection{Decidable SQL Predicate Fragment ($\mathcal{F}$)}
\label{sec:model_fragment}

To evaluate $\varphi_D \land \varphi_R$ in metadata time without touching data files, \systemname\ defines a static conjunctive fragment $\mathcal{F}$ over column names $c \in \mathcal{A}$ and literals $\ell$: $\varphi ::= t_1 \land \dots \land t_m$, where each atomic constraint $t_i$ takes one of three forms: (1)~binary comparisons $c \;\text{op}\; \ell$ with $\text{op} \in \{=, \neq, <>, \allowbreak <, \le, >, \ge\}$; (2)~finite set membership $c \;\texttt{IN}\; (\ell_1, \dots, \ell_k)$; or (3)~closed intervals $c \;\texttt{BETWEEN}\; \ell_{\text{low}}$ \texttt{AND} $\ell_{\text{high}}$. Clauses containing \texttt{OR}, \texttt{NOT}, arithmetic expressions, joins, or subqueries lie outside $\mathcal{F}$ and are conservatively routed to the delete-time row-value post-check (Section~\ref{sec:design_conflict}).

\section{System Architecture and Merge Design}
\label{sec:design}

\subsection{Architectural Overview}
\label{sec:design_arch}

Figure~\ref{fig:architecture} illustrates the architecture of \systemname. The system layers metadata-driven branch management and three-way semantic merge execution over an immutable cloud object store across four decoupled components:
\begin{enumerate}
    \item \textbf{Catalog and DAG Layer ($M_2$):} Maintains branch head pointers ($\texttt{heads}[b] \allowbreak\to \text{id}$) updated via atomic compare-and-swap (CAS), tracks the snapshot parent DAG, and caches ancestor-generation maps for sub-millisecond LCA discovery ($W_4, W_{\text{swarm}}$).
    \item \textbf{Commit Summary and SQL Predicate Layer ($M_1, M_3$):} Extracts read and delete predicates from SQL ASTs ($W_3$) and writes a compact commit summary (\texttt{manifests/\allowbreak<id>.summary.json}) with row deltas, schemas, predicates, and delete-time pre-images.
    \item \textbf{Three-Way Semantic Merge and VSA Engine ($M_1, M_2$):} Given tips $(T_A, T_B)$ and fork point $T_0$, replays non-merge commit summaries since $T_0$, executes the two-tier predicate verifier ($W_3$), unifies schemas ($W_4$), and reconciles row updates into converged records ($W_1$) or VSA choice nodes ($W_2$).
    \item \textbf{Deletion-Vector Storage Substrate ($M_3, M_4$):} Keeps base Parquet files immutable, encodes deleted and superseded row positions into serialized Roaring bitmaps~\cite{okolnychyi2024petabyte}, writes updates into a single delta Parquet file, and publishes a two-element delta manifest list at $O(\Delta_{\text{manifest}})$ S3 API cost ($W_1, W_4$).
\end{enumerate}

\subsection{Compact Commit Summaries and SQL Extraction}
\label{sec:design_summaries}

In standard Iceberg or Delta tables, discovering which rows changed between two snapshots requires reading manifest trees and scanning data files or change-data-capture logs. \systemname\ eliminates data scans during merge by writing one compact JSON summary per commit containing: (1)~parent snapshot IDs, branch name, and schema fields ($W_4$); (2)~modified file IDs and their updated descriptors, including base64-encoded Roaring DVs ($W_1$); (3)~row-level operations mapping each modified row ID to its operation kind, column assignments, and pre-image values upon deletion ($W_1, W_2, W_3$); (4)~attached predicates ($W_3$); and (5)~any open VSA choice nodes ($W_2$). Replaying a non-merge commit during a three-way merge issues exactly one object-store \texttt{GET} request for its summary object, regardless of whether the table contains $10^3$ or $10^5$ unchanged Parquet files.

Writers can attach predicates programmatically or pass raw SQL statements to \systemname's SQL extractor. The extractor parses \texttt{SELECT} and \texttt{DELETE} statements into an AST, normalizes the \texttt{WHERE} clause into canonical SQL text, and emits \texttt{reads\_}\allowbreak\texttt{where}$(\varphi_R)$ or \texttt{deletes\_}\allowbreak\texttt{where}$(\varphi_D)$. Queries containing joins, \texttt{UNION}, or subqueries retain their full clause text so the conflict verifier conservatively classifies them as outside $\mathcal{F}$ and falls back to the deleted-row check.

\subsection{DAG-Aware Delta Replay Since the Fork}
\label{sec:design_replay}

When long-running branches merge repeatedly across multi-stage pipelines ($W_4$), the commit history forms a DAG with nested merge diamonds rather than a simple tree. A naive three-way merge that inspects only the tip summary of each parent fails in two ways: first, a merge commit's summary does not duplicate ancestor predicates or rows parked in VSA choices, so a subsequent merge would forget earlier read or delete constraints ($W_3$); second, walking all ancestors of an internal merge commit without stripping commits already present in the new fork point $b = \text{LCA}(T_A, T_B)$ would either replay shared history prefixes as false conflicts ($W_1, W_2$) or drop commits whose parent predates $b$.

\bottomrule
\end{tabularx}

Algorithm~1 (\texttt{ReplaySinceFork}) reconstructs the exact folded delta $\Delta_t$ of branch tip $t$ since fork point $b$. First, it retrieves the cached ancestor set $\mathit{contained} = \text{anc}(b)$ and executes a post-order depth-first walk from $t$ that halts upon entering $\mathit{contained}$. Every commit in $\text{anc}(t) \setminus \text{anc}(b)$ is emitted once in topological order (parents before children), mapping any parent inside $\text{anc}(b)$ to $\mathit{folded}[b]$ via $\text{Known}(p)$.

Second, for each regular commit $u$, Algorithm~1 fetches $u$'s summary object (1 \texttt{GET}) and folds it onto its parent's delta via \texttt{FoldCommit}. If $u$ updates a row $r$ previously parked in an open VSA choice, \texttt{FoldCommit} resolves the VSA choice for $r$ and records the new write; if $u$ deletes $r$, it records $r$'s delete-time pre-image in $\sigma[r]$. Third, when the walk encounters an internal merge node $u$ with parents $(p_1, p_2)$, it locates $u$'s internal fork $f = \text{LCA}(p_1, p_2)$, strips the shared prefix $\mathit{folded}[f]$ from both parent deltas via \texttt{StripPrefix}, and combines their relative deltas without extra object-store reads.

\paragraph{1. Tier-1 Static Satisfiability (\texttt{Where\allowbreak Overlap}).}
For each pair of \texttt{deletes\_}\allowbreak\texttt{where}$(\varphi_D) \in \Delta_X.\Pi$ and \texttt{reads\_}\allowbreak\texttt{where}$(\varphi_R) \in \Delta_Y.\Pi$, \texttt{Where\allowbreak Overlap} tests whether $\varphi_D \land \varphi_R$ is satisfiable. When both clauses parse into the conjunctive fragment $\mathcal{F}$, atomic constraints are grouped by column $c$. For each column $c$, the solver maintains: (a) an allowed finite candidate set from $=$ and \texttt{IN} terms, (b) an excluded set from $\neq$ terms, (c) a greatest lower bound $(\mathit{low}, \mathit{inc}_{\text{low}})$ from $>$ and $\ge$ terms, and (d) a least upper bound $(\mathit{high}, \mathit{inc}_{\text{high}})$ from $<$ and $\le$ terms. Column $c$ is unsatisfiable iff the allowed candidate set contains no value within the active interval outside the excluded set, or $\mathit{low} > \mathit{high}$ (or $\mathit{low} = \mathit{high}$ with a strict inequality or excluded point). If any column is unsatisfiable, $\varphi_D \land \varphi_R$ is unsatisfiable and \texttt{Where\allowbreak Overlap} returns \texttt{False} in microseconds without reading a single table row. No row deleted under $\varphi_D$ can then satisfy $\varphi_R$ with its delete-time values; the one remaining case is a row that $X$ updated before deleting it, whose fork value (which $Y$ read) may still satisfy $\varphi_R$, so Line~8 checks the fork values of exactly those rows.

\paragraph{2. Tier-2 Deleted-Row Value Check (\texttt{AnyMatch}).}
When the static test cannot rule out an overlap, either because a clause falls outside $\mathcal{F}$ (e.g., \texttt{DELETE WHERE NOT} \texttt{kind = 'vip'}) or because the two clauses overlap on a region holding no deleted row, Lines~9--10 evaluate $\varphi_R$ on each deleted row's value at the fork and at delete time. Both values come from the commit summaries, so no data file is read. Clauses in $\mathcal{F}$ are evaluated directly, and any other single-table clause is evaluated by DuckDB~\cite{raasveldt2019duckdb} over those few rows. A row with no recorded value, or a read clause with a join or subquery that cannot be evaluated on its own, keeps the conflict. The check costs $O(|D_X|)$ per clause pair, so the static test is the fast path and the row check removes the false conflicts it leaves.

\paragraph{3. Lineage, Foreign-Key, and Domain Verification.}
Lines~4--5 intersect each \texttt{rows\_live} and \texttt{foreign\_key} set $I \in \Delta_Y.\Pi$ against $D_X$ in $O(\min(|I|, |D_X|))$ time. Lines~12--14 evaluate each $\texttt{domain}(\varphi_{\text{dom}}) \in \Delta_Y.\Pi$ against all $\texttt{insert}$ and $\texttt{update}$ assignments in $\Delta_X.\text{ops}$, flagging any record whose assigned columns violate $\varphi_{\text{dom}}$.

\subsection{Unified State Reconciliation Across $W_1$--$W_4$}
\label{sec:design_vsa}

Combining Algorithm~2 with Criteria~1--4 yields a unified decision and state-reconciliation procedure across $W_1$--$W_4$ (where at runtime, the $W_3$ and $W_4$ \texttt{block} checks execute first as fail-fast metadata guards prior to materializing $W_1$ and $W_2$ row deltas):
\begin{enumerate}[leftmargin=8pt, itemsep=0pt, topsep=1pt]
    \item \textbf{Disjoint row/column convergence ($W_1 \to \texttt{keep}$):} Under Criterion~1, rows modified by only one branch or identically on both adopt $\text{ops}_X(r)$. Rows updated on disjoint columns commute into $\rho_0(r) \oplus \Delta_A(r) \oplus \Delta_B(r)$ with zero false aborts ($M_1$).
    \item \textbf{Hotspot collision isolation in VSA ($W_2 \to \texttt{replan}$):} Under Criterion~2, if both branches assign distinct values $v_A \neq v_B$ to column $c$ (or update vs.\ delete), \systemname\ constructs a VSA choice node~\cite{zhu2018conflict} $\texttt{choice}(r, c, [(A, v_A), (B, v_B)]) \in \mathcal{V}_M$. Non-conflicting columns merge cleanly, while the cell retains its base value in the snapshot until resolved ($M_1, M_2$).
    \item \textbf{Semantic conflict blocking ($W_3 \to \texttt{block}$):} Under Criterion~3, if Algorithm~2 returns $V \neq \emptyset$, the merge halts immediately with $\texttt{semantic\_conflict}(V)$ before writing data, guaranteeing zero silent corruption ($M_1$).
    \item \textbf{Bidirectional schema unification ($W_4 \to \texttt{keep}/\texttt{block}$):} Under Criterion~4, additive nullable columns and numeric widenings ($\texttt{int32} \to \texttt{int64} \to \texttt{double}$) unify into $S_M$ without rewriting base files; incompatible column drops, renames, or narrowings halt with $\texttt{schema\_conflict}$ (\texttt{block}).
\end{enumerate}

\subsection{Zero-Copy Physical Merge over Deletion Vectors ($M_3, M_4$)}
\label{sec:design_physical}

\systemname\ materializes the merged snapshot $T_M$ without rewriting any base Parquet file ($M_3, M_4$). For every row $r$ updated or deleted in $\text{ops}_M$ that resided in a base file $f$ at zero-based offset $\text{pos}_0[r]$, \systemname\ sets bit $\text{pos}_0[r]$ in $f$'s Roaring deletion vector ($\text{DV}_M(f) = \text{DV}_A(f) \cup \text{DV}_B(f) \cup \{\text{pos}_0[r]\}$). All newly inserted records and resolved row updates across both branches are serialized into a single compact delta Parquet file (\texttt{data/<id>/delta-<id>.parquet}).

The commit protocol then writes three small metadata objects: (1)~the merge summary \texttt{manifests/\allowbreak<id>.summary.json}, (2)~a delta manifest \texttt{manifests/\allowbreak<id>.delta.json} containing descriptors only for files whose DV or payload changed since $T_0$, and (3)~a two-element manifest list \texttt{[base\_manifest\_key,\allowbreak delta\_key]}. Because untouched base file descriptors are inherited by reference, S3 API requests scale as $O(\Delta_{\text{manifest}})$ ($M_3$). During subsequent analytical queries ($M_4$), the scan engine inspects each row group's DV: clean row groups ($\text{DV} = \emptyset$) execute native vectorized Parquet scans without filtering overhead, while background compaction periodically folds DVs back into base files once the dirty-row ratio or scan-to-merge ratio crosses the cost threshold.

\subsection{Extension: Commit Service for Agent Swarms ($W_{\text{swarm}}$)}
\label{sec:design_swarm}

To support the composite agent-swarm workload $W_{\text{swarm}}$ beyond standard WAP pipelines, \systemname\ provides a server-side CAS merge service. When $k$ agents concurrently invoke $\text{CAS}(\texttt{main},\allowbreak T_{\text{expected}},\allowbreak T_{\text{local}})$, the $k-1$ losing branches are not aborted; instead, the server executes a three-way semantic merge between each losing snapshot and the advancing head ($M_1$), and returns a commit that conflicts with the head to its agent. With one CAS per commit, throughput is bounded by each merge's catalog and object-store round trips ($M_2$). With \emph{group commit}, the service takes up to $G$ queued commits, merges them one by one onto the head in memory, and publishes the batch with a single catalog CAS. In this paper the service runs inside the swarm simulation of Section~\ref{sec:eval_swarm}.

\section{Correctness, Complexity, and Scan Overhead Analysis}
\label{sec:correctness}

We now establish formal guarantees for \systemname\ across all four evaluation metrics: semantic correctness ($M_1$), merge latency complexity ($M_2$), cloud S3 API and write amplification bounds ($M_3$), and post-merge analytical scan overhead ($M_4$).

\subsection{Soundness and Exactness Proofs ($M_1$)}
\label{sec:correctness_proofs}

\begin{theorem}[Soundness]
\label{thm:soundness}
Let $T_A$ and $T_B$ be two branches with fork point $T_0$, and suppose every row deleted on a branch is deleted by a statement whose \texttt{deletes\_where} clause the row satisfied at delete time, and that the commit summaries record each deleted row's pre-image. If Algorithm~2 returns $V = \emptyset$ for the deltas produced by Algorithm~1 and \systemname\ commits $T_M = \text{merge}(T_0, T_A, T_B)$, then $T_M$ is purge-safe (Definition~\ref{def:purge_safe}) and satisfies Criteria~1--4 across $W_1$--$W_4$.
\end{theorem}

\begin{proof}
We verify Conditions~1--3 of Definition~\ref{def:purge_safe}. For Condition~2, Lines~4--5 of Algorithm~2 test $p.\text{row\_ids} \cap D_X \neq \emptyset$ for all $\texttt{rows\_live}$ and $\texttt{foreign\_key}$ predicates on both branches; $V = \emptyset$ guarantees $D_A \cap I = \emptyset$ and $D_B \cap I = \emptyset$. For Condition~3, Lines~12--14 test every conjunct of each $\texttt{domain}(\varphi_{\text{dom}})$ predicate against all $\texttt{insert}$ and $\texttt{update}$ assignments on the partner branch; $V = \emptyset$ guarantees all assigned column values satisfy $\varphi_{\text{dom}}$.

For Condition~1, fix $\texttt{reads\_where}(\varphi_R) \in \Pi(Y)$ and $r \in D(X)$. By assumption, $\sigma_X(r) \models \varphi_D$ for some $\texttt{deletes\_where}(\varphi_D) \in \Pi(X)$. If \texttt{WhereOverlap} is true, Lines~9--10 found that neither $\rho_0(r)$ nor $\sigma_X(r)$ satisfies $\varphi_R$. Otherwise, \texttt{WhereOverlap} returns $\texttt{False}$ only if there exists a column $c$ whose combined constraint set $T_c(\varphi_D) \cup T_c(\varphi_R)$ is unsatisfiable: either the intersection of equality and \texttt{IN} sets contains no candidate within $[\mathit{low}, \mathit{high}]$ outside the $\neq$ exclusions, or $\mathit{low} > \mathit{high}$ (or $\mathit{low} = \mathit{high}$ with a strict bound or excluded point). In either case, no value $v$ in the domain of column $c$ satisfies $T_c(\varphi_D) \land T_c(\varphi_R)$. Hence $\varphi_D \land \varphi_R$ is unsatisfiable, so $\sigma_X(r) \not\models \varphi_R$; if $r \in \mathit{moved}_X$, Line~10 found $\rho_0(r) \not\models \varphi_R$, and otherwise $\rho_0(r) = \sigma_X(r)$. Criteria~1, 2, and~4 follow directly from the column-disjoint composition, VSA encapsulation, and $\preceq_{\text{type}}$ schema unification rules in Section~\ref{sec:design_vsa}.
\end{proof}

\begin{lemma}[Exact DAG Replay Since the Fork]
\label{lem:replay}
For any branch tip $t$ and fork point $b = \text{LCA}(t_{\text{left}}, t_{\text{right}})$, Algorithm~1 folds every non-merge commit $c \in \text{anc}(t) \setminus \text{anc}(b)$ once in topological order, excludes every commit in $\text{anc}(b)$, and preserves all predicates and open VSA choices across intermediate clean merges.
\end{lemma}

\begin{proof}
In Algorithm~1, $\mathit{contained} = \text{anc}(b)$ is the complete ancestor set of $b$. The post-order DFS from $t$ halts along any edge entering $\mathit{contained}$ and emits each node $u \notin \mathit{contained}$ only after all of its parents outside $\mathit{contained}$ have been emitted, yielding $\text{anc}(t) \setminus \text{anc}(b)$ in topological order. Crucially, halting on $\text{anc}(b)$ prevents dropping valid branch commits in multi-merge chains: if a report branch $R$ (forked from $T_0$) merges with an update branch $U$ to form $M_1$, and $M_1$ later merges with a purge branch $P$ that forked from $U$, the new LCA is $b = U$. Even though $R$ is not a descendant of $U$, $R \in \text{anc}(M_1) \setminus \text{anc}(U)$ is retained and its parent $T_0 \in \text{anc}(U)$ maps to $\mathit{folded}[b]$ via $\text{Known}(p)$, preserving $R$'s read predicate. Meanwhile, for any internal merge node $u$ with fork $f$, \texttt{StripPrefix} removes $\mathit{folded}[f]$ before combining its parents, ensuring shared history prefixes are never double-counted as concurrent conflicts.
\end{proof}

\subsection{Precision, Complexity, and Scan Overhead Bounds ($M_1$--$M_4$)}
\label{sec:correctness_complexity}

\paragraph{Precision Boundaries ($M_1$).}
While Theorem~\ref{thm:soundness} and Lemma~\ref{lem:replay} guarantee zero false negatives (1.00 recall) on $W_3, W_4$ and zero false aborts on $W_1$, the check can still produce false positives when: (a) the read clause contains a join or subquery and cannot be evaluated against the deleted rows on its own, or (b) a row entered the read range only on branch $X$ before being deleted, which Definition~\ref{def:purge_safe} conservatively counts. Randomized tests check Theorem~\ref{thm:soundness}: \FuzzSeeds\ random branch pairs, run directly and again after an intermediate merge, with both merge orders and against a brute-force oracle, find no missed conflict.

\paragraph{Merge Time and Cloud S3 API Complexity ($M_2, M_3$).}
Let $K = |\mathcal{C}(T_0, T_A)| + |\mathcal{C}(T_0, T_B)|$ be the number of non-merge commits since $T_0$, $|\Delta_{\text{rows}}|$ be the number of modified rows, $|\Delta_{\text{files}}|$ be the number of touched files, and $|\Pi|$ be the number of attached predicates. Algorithm~1 issues at most $K$ object-store \texttt{GET} requests ($M_3$), Algorithm~2 and VSA reconciliation run in $O(|\Pi_A| \cdot |\Pi_B| + |\Delta_{\text{rows}}|)$ CPU time ($M_2$), and physical publication writes 1 delta Parquet file plus 3 small JSON objects (4 \texttt{PUT}s), yielding $O(K + |\Delta_{\text{files}}|)$ total S3 API cost and $\text{WAF} = 1 + B_{\text{meta}} / B_{\Delta\text{rows}} \approx 1$ ($M_3$)---independent of total table file count $N_{\text{files}}$ and row count $N_{\text{rows}}$.

\paragraph{Post-Merge Analytical Scan Overhead Bound ($M_4$).}
Let a table span $G_{\text{rg}}$ Parquet row groups, and let $G_{\text{dirty}} \le G_{\text{rg}}$ be the number of row groups with non-empty Roaring DVs after merging. Because clean row groups ($\text{DV} = \emptyset$) execute native vectorized scans at base cost $C_{\text{scan}}$ while each dirty row group incurs a relative bitmap-mask factor $\alpha$, post-merge query latency is bounded by $T_{\text{scan}}(T_M) = C_{\text{scan}} \cdot (1 + \alpha \cdot \frac{G_{\text{dirty}}}{G_{\text{rg}}})$. For localized updates ($W_1$, where $G_{\text{dirty}} \ll G_{\text{rg}}$), relative scan overhead approaches $0$. When cumulative scan overhead across $N_{\text{scans}}$ queries exceeds compaction rewrite cost $C_{\text{compact}}$ (at crossover point $N_{\text{scans}}^* = \frac{C_{\text{compact}}}{\alpha \cdot C_{\text{scan}} \cdot (G_{\text{dirty}} / G_{\text{rg}})}$), background compaction folds DVs into clean base files and resets $G_{\text{dirty}} \to 0$.

\section{Implementation}
\label{sec:impl}

We implemented \systemname\ in Python (about \EngineLines\ lines of engine code in six modules: \texttt{metadata.py}, \texttt{storage.py}, \texttt{merge.py}, \texttt{verification.py}, \texttt{sql\_}\allowbreak\texttt{predicates.py} and \allowbreak\texttt{baselines.py}, plus about \BenchLines\ lines of benchmark code).

Data files are encoded as Apache Parquet objects via \texttt{pyarrow}, with a hidden \texttt{\_\_row\_id} column tracking Iceberg v3 row lineage~\cite{iceberg2025v3}. Positional deletion vectors are implemented using \texttt{pyroaring} (\texttt{BitMap.}\allowbreak\texttt{serialize} and bitwise union \texttt{|}). Analytical queries in metric $M_4$ execute in DuckDB over Parquet files on local storage; the read experiments store a DV as a Parquet mask of booleans and apply it with a positional join, while clean row groups are read without a mask. To support deep commit histories and high-concurrency branching with minimal memory footprint, snapshot row states use a copy-on-write structural overlay (\texttt{RowView}): each commit stores only modified records and deleted row IDs, walking the parent chain on lookup without copying unchanged rows. In the commit graph, each snapshot caches its ancestor-generation map upon creation, allowing \texttt{lca} to run a generation-ordered max-heap search that terminates as soon as the highest open generation falls below the best common ancestor found.

To profile cloud storage costs deterministically ($M_3$), our in-memory object store logs exact counts of \texttt{PUT}, \texttt{GET}, and \texttt{LIST} calls and transferred bytes, applying public AWS S3 Standard (\texttt{us-east-1}) pricing (\$0.005 per 1,000 \texttt{PUT}/\texttt{LIST} calls, \$0.0004 per 1,000 \texttt{GET} calls~\cite{s3pricing}) and the analytical cloud latency model $T_{\text{est}} = T_{\text{cpu}} + \allowbreak N_{\text{put}} \cdot 100\,\text{ms} + \allowbreak N_{\text{get}} \cdot 30\,\text{ms} + \allowbreak N_{\text{list}} \cdot 50\,\text{ms} + \allowbreak B_{\text{put}} / (100\,\text{MB/s})$. All reported CPU latencies are real wall-clock measurements without artificial \texttt{sleep()} calls; no experiment runs against S3. $B_1$, $B_1\text{R}$, $B_2$ and $B_6$ are rule models evaluated on the same snapshots as \systemname: they compute what each system's documented rule decides, and a test confirms $B_1$'s rule against a real \texttt{delta-rs} table. $B_3$ and $B_4$ are our reimplementations, and $B_5$ is the Dolt binary driven through its SQL interface with \texttt{dolt merge}. Compaction and the group-commit service are implemented in the benchmark harness.

\label{sec:eval}

\subsection{Experimental Setup and Baselines}
\label{sec:eval_setup}

All experiments execute on one machine with \MachineCores\ cores, Python~\PythonVersion, DuckDB~\DuckdbVersion, \texttt{pyarrow}~\PyarrowVersion, \texttt{pyroaring}, \allowbreak\texttt{sqlglot}, and Dolt. TPC-H data is real \texttt{lineitem} generated with \texttt{tpchgen-cli}, a port of the TPC-H generator~\cite{tpch}. Timed merges run once untimed and then \Repeats\ times, and we report the median with the range; DuckDB scans run in separate processes; the swarm runs \SwarmSeeds\ seeds and reports means with 95\% confidence intervals. Following the Branch-Execute-Merge protocol adapted from LST-Bench~\cite{camacho2024lstbench}, we evaluate all workloads in canonical order: $W_1$ (shared-file disjoint updates), $W_2$ (hotspot key contention $\rho \in [0\%, 20\%]$), $W_3$ (cross-branch predicate conflicts over a 27-case labelled semantic suite spanning $W_1, W_3, W_4$ and \TpchPairs\ TPC-H~\cite{tpch} refresh-versus-query branch pairs), $W_4$ (schema evolution and manifest/DAG scaling from 1K to 10K files and \HistLow\ to \HistHigh\ snapshots), and the extension workload $W_{\text{swarm}}$ (8 to 64 concurrent agents combining $W_1$--$W_3$).

Following Table~\ref{tab:existing_merges}, we compare \systemname\ against all six baseline families in canonical order ($B_1, B_1\text{R}, B_2, B_3, B_4, B_5, B_6$): \textbf{$B_1$} (File-level OCC~\cite{armbrust2020delta}), \textbf{$B_1\text{R}$} (Delta row-write variant of $B_1$ with file-level read conflict checks~\cite{delta2024rowlevel}), \textbf{$B_2$} (Copy-on-Write row merge~\cite{tagliabue2024bauplan}), \textbf{$B_3$} (Relational tuple versioning~\cite{maddox2016decibel, huang2017orpheusdb}), \textbf{$B_4$} (Automatic CRDT views~\cite{faria2025crdv}), \textbf{$B_5$} (Constraint-aware cell merge, the Dolt binary executing native \texttt{dolt merge} with SQL \texttt{FOREIGN KEY} and \texttt{CHECK} constraints~\cite{dolt2026}), and \textbf{$B_6$} (Classical SSI~\cite{cahill2008serializable}, detecting two-edge $\mathit{rw}$-\allowbreak antidependency cycles). All baselines ($B_1$--$B_6$ and $B_1\text{R}$) are evaluated on semantic conflict detection ($M_1$, Table~\ref{tab:correctness}); because $B_5$ uses a monolithic Prolly-tree engine and $B_6$ uses volatile OLTP \texttt{SIREAD} locks without S3 Parquet manifests, physical S3/\allowbreak Parquet storage and catalog benchmarks ($M_2$--$M_4$, Sections~\ref{sec:eval_scale}--\allowbreak\ref{sec:eval_swarm}) evaluate the cloud lakehouse and dataset-versioning architectures ($B_1, B_1\text{R}, B_2, B_3, B_4$).

Table~\ref{tab:correctness} evaluates conflict recall and precision ($M_1$) across all baselines ($B_1$--$B_6$ and $B_1\text{R}$) on two benchmarks: (a) the 27 labelled merge scenarios spanning $W_1$ (shared-file disjoint updates), $W_3$ (equality, range, \texttt{BETWEEN}, \texttt{IN}, multi-column \texttt{AND}, boundary $\le 3$ vs.\ $\ge 3$, $\neq$, unparsed \texttt{NOT}/\texttt{OR}, domain invariants, foreign keys, and \texttt{rows\_live}), and $W_4$ (additive schema evolution); and (b) \TpchPairs\ TPC-H~\cite{tpch} branch pairs ($W_3$) on real \texttt{lineitem} at scale factor \TpchSF\ (\TpchRows\ rows sorted by \texttt{l\_shipdate} in \TpchFiles\ files), pitting six refresh branches (four ship-date purges and two RF2-style deletes of order keys) against seven report branches that read with the \texttt{lineitem} filters of Q1, Q3, Q6, Q7, Q10, Q12 and Q14. Examining the systems in canonical order: $B_1$ (File OCC) tracks only physical file writes and scores 0.00 recall across both suites while suffering false aborts on $W_1$. $B_1\text{R}$ (Delta-style file-read tracking) catches the read-delete hazards whose rows share a file with the deleted rows (recall \BoneRSuiteRec\ on the 27-case suite, missing domain/FK invariants; recall \BoneRTpchRec\ on TPC-H), but blocks \BoneRSuiteFP\ safe merges on the 27-case suite (precision \BoneRSuitePrec) and \BoneRTpchFP\ safe TPC-H pairs (precision \BoneRTpchPrec) whose purges delete rows in files the report scanned. Row/tuple/CRDT baselines $B_2, B_3,$ and $B_4$ lack predicate verification and score 0.00 recall on both benchmarks. $B_5$ (Dolt) achieves recall \DoltSuiteRec\ (\DoltSuiteTP/\SuitePos) on the 27-case suite and \DoltTpchRec\ on TPC-H: it catches the declared \texttt{FOREIGN KEY} and \texttt{CHECK} cases, but a report's filter cannot be declared as a table constraint ($W_3$), and Dolt refuses to add a \texttt{CHECK} constraint that legacy rows in $T_0$ violate. Confirming Proposition~\ref{prop:serializability}, $B_6$ (Classical SSI) also scores 0.00 recall across both benchmarks: because a report branch $T_B$ and a purge branch $T_A$ induce only a single one-way dependency $T_B \xrightarrow{\mathit{rw}} T_A$ (serializable as $T_B \prec T_A$) without a back-edge $T_A \xrightarrow{\mathit{rw}} T_B$, SSI's dangerous-structure detector never triggers. By contrast, \systemname\ achieves \textbf{\SemSuiteRec\ recall} (\SemSuiteTP/\SuitePos) and \textbf{\SemSuitePrec\ precision} on the 27-case suite, and \textbf{\SemTpchRec\ recall} (\TpchPos/\TpchPos) with \textbf{\SemTpchPrec\ precision} on TPC-H; with the deleted-row check disabled, precision falls to \StaticSuitePrec\ and \StaticTpchPrec.

Figure~\ref{fig:selectivity} further isolates the impact of delete selectivity ($W_3$) on false blocks. A report reads with Q6's filter, which touches \SelQsixFiles\ of the \TpchFiles\ files, and a purge deletes a random range of part keys restricted to discounts Q6 does not read, so no pair is a true conflict; each point is \SelTrials\ purges in three clause forms (conjunctive, \texttt{NOT} and \texttt{OR}), deleting from \SelMinPct\% to \SelMaxPct\% of the table. $B_1\text{R}$ blocks the report as soon as the purge touches one of the files Q6 reads: its false-block rate is \BoneRSelAtOne\ at 0.1\% of rows. Static-only \systemname\ blocks the \texttt{NOT} and \texttt{OR} forms (rate \StaticSelMean), whereas full \systemname\ (static solver plus Tier-2 deleted-row check) achieves a \textbf{\SemSelMax\ false-block rate} across the entire selectivity spectrum.

\noindent\textbf{Key Insight ($M_1$):} \emph{Predicate-level verification over commit summaries completely eliminates silent read-delete and domain corruption ($W_3$) with 1.00 recall, avoiding both the low recall of $B_1, B_2$--$B_6$ and the false blocks of file-granularity read tracking ($B_1\text{R}$).}

\subsection{Merge Latency and Metadata Scalability ($M_2$)}
\label{sec:eval_scale}

Figure~\ref{fig:scalability} evaluates three-way merge CPU latency ($M_2$) across three scaling dimensions ordered by workload ($W_2 \to W_4$): (1)~\textbf{Hotspot row contention ($W_2$, Figure~\ref{fig:scalability}a):} on a 10,000-file table, \systemname\ merges in \WtwoSemZero\,ms at $\rho = 0$ and \WtwoSemTwenty\,ms at $\rho = 20\%$, where colliding cells become VSA choice nodes; $B_1$ takes \WtwoBoneZero\,ms and \WtwoBoneTwenty\,ms because it compares full file lists. $B_4$ takes \WtwoBfourZero\,ms at $\rho = 0$, but it checks nothing: it overwrites one side of every collision. (2)~\textbf{Manifest depth ($W_4$, Figure~\ref{fig:scalability}b):} as the manifest grows from 1K to 10K Parquet files, \systemname\ merges a schema change and an append in \WfourSemOne\,ms and \WfourSemTen\,ms, while $B_1$, $B_2$ and $B_3$ take \WfourBoneTen\,ms, \WfourBtwoTen\,ms and \WfourBthreeTen\,ms at 10K files, and $B_3$ issues \WfourBthreeReq\ object-store calls to rebuild its dictionaries. (3)~\textbf{Commit DAG history depth ($W_4$, Figure~\ref{fig:scalability}c):} from \HistLow\ to \HistHigh\ snapshots, generation-pruned LCA discovery takes \HistLca\,$\mu$s and the merge \HistSemLow\,ms and \HistSemHigh\,ms. Each merge here replays one commit per side, so replay does not explain the growth; the merge also lists the manifest prefix, which grows with the history in our store, and we did not isolate the cause further. CPU time is not the whole story: under the latency model of Section~\ref{sec:impl}, a $W_2$ merge at $\rho = 0$ is estimated at \WtwoSemEst\,s for \systemname\ and \WtwoBoneEst\,s for $B_1$, because \systemname\ reads one summary per commit and writes more metadata objects.

\noindent\textbf{Key Insight ($M_2$):} \emph{By isolating hotspot cell collisions in VSA choice nodes ($W_2$) and inheriting unchanged file descriptors by reference ($W_4$), \systemname\ prevents contention-induced abort storms and keeps merge CPU time 40--50$\times$ below the file-level baselines at 10K files, with a request count independent of $N_{\text{files}}$.}

\subsection{Cloud Object-Store Cost Efficiency ($M_3$)}
\label{sec:eval_cost}

Figure~\ref{fig:s3_cost} evaluates S3 request counts and write amplification ($M_3$) on $W_1$ across a 10,000-file table where two branches update disjoint rows across 5,000 files each. \systemname\ completes the merge in \textbf{7 S3 requests} (3 \texttt{PUT}, 3 \texttt{GET}, 1 \texttt{LIST}), writing \WoneSBytesSem\ bytes of metadata (\$0.0000212) and rewriting no base file. Copy-on-Write $B_2$ reads and rewrites all 10,000 modified files, issuing 20,007 S3 requests (10,001 \texttt{PUT}, 10,005 \texttt{GET}, 1 \texttt{LIST}) at \$0.054012---a \textbf{99.96\% S3 request-cost reduction} for \systemname. $B_1$ issues only \WoneSReqBone\ requests, but it aborts this merge. Similarly, on $W_4$, \systemname\ issues 7 S3 requests ($O(\Delta_{\text{manifest}})$) compared to 20,009 requests in $B_3$.

While keeping deletion vectors uncompacted minimizes merge-time write I/O ($M_3$), it introduces bitmap filtering work during subsequent analytical reads ($M_4$). Validating the crossover bound $N_{\text{scans}}^*$ from Section~\ref{sec:correctness_complexity}, Figure~\ref{fig:cost_crossover} models total dollar cost per 1,000 merges (combining the measured S3 API requests, one day of S3 storage for written bytes, 128\,MiB Parquet file rewrites for $B_2$, and CPU at \$0.10/hour, using the scan overheads of Table~\ref{tab:scan}) against downstream full-table scans per merge: (1)~at 10 scans per merge, 1,000 merges with open DVs cost \CostSemLoc\ in \systemname\ for localized deletes (\CostSemUni\ for uniform deletes) vs.\ \CostBtwo\ for CoW $B_2$; (2)~leaving DVs open stays cheaper than rewriting until \textbf{\CrossLoc\ scans per merge} when deletes are localized to a single row group ($W_1$), and \textbf{\CrossUni\ scans per merge} when uniform deletes dirty every row group. Past that point the merged files should be compacted (Section~\ref{sec:eval_read}).

\noindent\textbf{Key Insight ($M_3$):} \emph{Compiling branch merges into Roaring DV unions and delta manifests cuts object-store requests by about three orders of magnitude, remaining more cost-effective than eager CoW rewrites ($B_2$) for up to \CrossUni--\CrossLoc\ downstream full-table scans per merge.}

\subsection{Ablation Studies}
\label{sec:eval_ablation}

We isolate four core design choices in \systemname\ ordered by workload ($W_1 \to W_3 \to W_4 \to W_{\text{swarm}}$): (1)~\textbf{Parquet file packing density ($W_1 \to M_1$, Figure~\ref{fig:ablations}a):} two branches each update \PackChanged\ random rows of a \PackRows-row table; as rows packed per Parquet file increase from 1 to \PackMax, $B_1$'s false-abort rate climbs from 0 to \PackBoneMax, whereas $B_1\text{R}$ and \systemname\ maintain a \textbf{0\% false-abort rate} regardless of file size because both compare rows. (2)~\textbf{Tier-2 deleted-row check ($W_3 \to M_1$, Figure~\ref{fig:selectivity}):} disabling \texttt{AnyMatch} in Algorithm~2 leaves recall unchanged but lowers precision from \SemSuitePrec\ to \StaticSuitePrec\ on the 27-case suite and from \SemTpchPrec\ to \StaticTpchPrec\ on the TPC-H pairs, and raises the false-block rate for the \texttt{NOT} and \texttt{OR} forms in Figure~\ref{fig:selectivity} from \SemSelMax\ to \StaticSelMean. (3)~\textbf{Exact DAG replay since the fork ($W_4 \to M_1$):} reading only the tips' summaries loses the predicates of commits merged earlier: the edge-case tests include a report that was merged once before it meets a purge, which tip-only replay merges and Algorithm~1 blocks; with Algorithm~1, \FuzzSeeds\ randomized seeds find no missed hazard. (4)~\textbf{Catalog commit-path batching ($W_{\text{swarm}} \to M_2$, Figure~\ref{fig:ablations}b):} with a \SwarmRtt\,ms catalog round trip, one CAS per commit reaches \SwarmSemSixtyFour\ commits/s at \SwarmMaxAgents\ agents, whereas group commit ($G=\SwarmGroup$) reaches \textbf{\SwarmGroupSixtyFour\ commits/s}.

\section{Related Work}
\label{sec:related}

\paragraph{Lakehouse Storage and Row-Level Operations.}
Delta Lake~\cite{armbrust2020delta}, the Lakehouse paradigm~\cite{zaharia2021lakehouse}, and comparative storage studies~\cite{jain2023analyzing, camacho2024lstbench, harby2025survey} established metadata-driven ACID transactions over cloud object stores. Okolnychyi et~al.~\cite{okolnychyi2024petabyte}, Apache Iceberg v3~\cite{iceberg2025v3}, and Delta Lake deletion vectors~\cite{delta2024rowlevel} introduced Roaring DVs and row lineage for single-branch MoR updates, while Apache Hudi~\cite{sumit2026hudi} and Lance~\cite{lance2025} provide multi-modal metadata and point-lookup indices. Durner et~al.~\cite{durner2023exploiting} quantified the S3 request-cost model motivating our $O(\Delta_{\text{manifest}})$ design. LakeVilla~\cite{gotz2025lakevilla}, Götz et~al.~\cite{gotz2026interoperable}, and TreeCat~\cite{oh2025treecat} coordinate multi-table commits and catalog trees, but omit cross-branch predicate conflict verification.

\paragraph{Dataset Versioning and Branching.}
Dataset versioning principles~\cite{bhattacherjee2015principles}, DataHub~\cite{bhardwaj2015datahub}, Decibel~\cite{maddox2016decibel}, OrpheusDB~\cite{huang2017orpheusdb}, and ForkBase~\cite{wang2018forkbase} pioneered storage layouts for branched datasets. Bauplan~\cite{tagliabue2024bauplan} provides zero-copy branch references for cloud WAP pipelines, and Dolt~\cite{dolt2026} performs cell-level merges over Prolly trees with SQL schema constraints, missing query read predicates and partial-domain invariants.

\paragraph{Program Merge and Version-Space Algebra.}
Sousa et~al.~\cite{sousa2018verified} formalized verified three-way program merge over ASTs, Zhu and He~\cite{zhu2018conflict} introduced VSA to represent conflicting AST candidates, and Zhu et~al.~\cite{zhu2024methodology} combined top-down and bottom-up traversals. Subsequent work detects behavioral conflicts via unit tests~\cite{dasilva2024detecting} or static analysis~\cite{dejesus2024lightweight}. \systemname\ brings verified three-way merge and VSA from ASTs to cloud lakehouses by lifting verification to SQL commit predicates and Roaring DVs.

\paragraph{Concurrency Theory and Replicated Views.}
Eswaran et~al.~\cite{eswaran1976notions} introduced predicate locks, Adya~\cite{adya1999weak} formalized multi-version dependency graphs, and Cahill et~al.~\cite{cahill2008serializable} developed Serializable Snapshot Isolation (SSI). Proposition~\ref{prop:serializability} shows that purge-safe branch merging and two-branch serializability are incomparable, because both branches' outputs coexist in $T_M$. CRDTs~\cite{almeida2024crdt} and CRDV~\cite{faria2025crdv} guarantee automatic state convergence without branch isolation or semantic conflict blocking.

\paragraph{Extensions to Agentic Systems.}
Git4Data~\cite{git4data2026} and Chronos~\cite{zhou2026chronos} provide copy-on-write and bolt-on branching for AI agents, BranchBench~\cite{ang2026branchbench} evaluates branching vs.\ query latency under agentic workloads, and ATR~\cite{lyu2026atr} studies selective revalidation for long-running agents. \systemname\ complements these substrates with the missing three-way semantic merge engine over cloud lakehouses.

\section{Limitations and Conclusion}
\label{sec:conclusion}

Our evaluation highlights four limitations pointing to future work: (1)~\emph{Direct cloud integration}: Parquet I/O, bitmaps, DuckDB scans, and Dolt runs are physical, but the object store is in memory and S3 costs and latencies are modelled; $B_1$, $B_1\text{R}$, $B_2$ and $B_6$ are rule models, and the swarm is a simulation. Native AWS S3 and Iceberg v3 Puffin integration is planned. (2)~\emph{Predicate scope}: purge-safety covers deletes, not updates that move rows out of a read range, and a read clause with a join or subquery cannot be checked against rows and is treated as overlapping. (3)~\emph{Scale and scans}: the TPC-H pairs use scale factor \TpchSF\ and the read experiments scale factor 1 on one thread; DVs are applied through a Parquet mask and a positional join rather than a native bitmap reader, and compaction lives in the benchmark harness. (4)~\emph{Multi-table merges}: extending group commit to multi-table lakehouse transactions~\cite{gotz2025lakevilla, gotz2026interoperable} remains open.

\systemname\ brings verified three-way semantic merge to branched data lakehouses. By decoupling predicate-level conflict verification over compact commit summaries from zero-copy physical reconciliation over Roaring deletion vectors, \systemname\ eliminates silent semantic corruption across lakehouse pipelines and concurrent agent workloads while scaling cloud API cost solely with branch delta size.
